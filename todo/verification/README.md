# 同期の形式検証（TLA+）

`SyncTodo.tla` は、このアプリの同期（`src/sync.ts`・`src/server-store.ts`・`src/api.ts`・`src/app.ts`）を、2 つのタブとサーバのモデルにしたもの。TLC で、送信・失敗・タイムアウト・遅れて届く要求・pull・リロード・タブを閉じることが**どの順に起きても**次の 4 つが守られるかを全部の順番について調べる。

- `AckedMeansApplied`: 確認が来たとして送信待ちから外した操作は、その操作としてサーバに反映されている
- `ClientOrderKept`: 同じクライアント ID の操作は、サーバで連番の順に 1 回ずつ反映処理される（再送が二重にならない・古い再送が巻き戻さない）
- `Converged`: 送信待ちも届く途中の要求も無く、全タブが最後まで pull したら、全タブの一覧がサーバと同じ
- `NoOpLost`: ユーザーが積んだ操作は、サーバに反映済みか、開いているタブの送信待ちか、届く途中の要求にある

## 見つかったこと（公開時点のコード。どれも本物のコードで再現済み）

1. **タブを複製すると、片方のタブの操作が黙って捨てられる。** 複製したタブには sessionStorage が写るので、2 つのタブが同じクライアント ID と同じ `nextOpNo` を持つ。両方で操作すると同じ opId が 2 つでき、サーバはあとから届いた方を「再送」と見なして反映しない。そのタブは送信待ちから外し、「同期済み」と出る。重なったのが追加なら、その todo は作られず画面からも消える。
2. **複製したタブ同士は同じ localStorage のキーに保存を上書きし合う。** どちらかをリロードすると、もう一方のタブの状態を読み、自分のまだ送っていない操作が消える。
3. **送信待ちが残ったタブを閉じると、その操作は二度と送られない。** 開き直したタブは新しいクライアント ID を作り、古いキーを読まない。

README の「同じ URL を別タブで開くと、それぞれ別のクライアントになる」はタブの複製では成り立たず、「変更は「送信待ち」として残り、つながったら送られる」はタブを閉じると成り立たない。直し方の候補と、やってはいけない直し方（起動ごとに ID を作り直すと、リロードのたびに送信待ちが消える）は SKILL.md の「直し方の候補」。

付録C Lean は Rust と相性がよく、JavaScript とは相性が悪い

本編では todo の中核を Rust で書き、Lean に翻訳して証明しました。同じ todo でも、JavaScript／TypeScript 版（付録D・F）では証明をせず、MBT（モデルに基づくテスト。仕様から作った操作の列を実装に流して突き合わせる）とモデル検査にしました。この付録では、その分け方の理由を説明します。

この付録のゴール

  • Rust の所有権と借用があると、書き換えを「新しい値を返す」関数に直せる理由を説明できる
  • 翻訳の限界と、翻訳で信頼している部分を言える
  • JavaScript のコードを証明しにくい理由を、具体的なコードで説明できる
  • 証明する核を Rust に切り出し、外側は JS/TS のままにする分け方を説明できる

Lean の関数は書き換えをしない

Lean の関数は純粋な関数です。同じ引数なら同じ値を返し、引数を書き換えません。証明はこの性質に頼っています。「t に足したあとの t」を、普通の式として扱えるからです。

一方、実際のプログラムは値を書き換えます。証明するには、書き換えを「新しい値を返す」に置き換える必要があります。置き換えてよいのは、書き換えられる値を、ほかの誰も見ていないときだけです。誰かが同じ値を見ていると、その人から見た値も一緒に変わるので、「新しい値を返す」では表せません。同じ値を2つの名前から見ている状態を別名（エイリアス）と呼びます。

Rust は別名を型で禁じている

Rust の &mut（書き換えてよい借用）は、借りている間ほかの誰も同じ値を見られません。コンパイラがこれを検査します。だから Aeneas は、&mut Todos を受け取る関数を「Todos を受け取り、新しい Todos を返す」関数に直せます。メモリやアドレスを Lean で扱う必要がありません。Aeneas の論文 Aeneas: Rust Verification by Functional Translation（ICFP 2022）は、この考え方を「借用の規則に頼って、メモリの推論を要らなくする」と述べています。

本編の add を並べます。上が手で書いた Rust、下が Charon（Rust のコンパイラから中間表現を取り出す道具）→ Aeneas が自動で作った Lean です。

違いは3つです。

  • 引数の &mut Todos が、ただの Todos になった
  • 戻り値が「元の戻り値 × 新しい Todos」の組になった。書き換えた結果は、戻り値として外に出る
  • 全体が Result に包まれた。id + 1 のあふれや添字の範囲外は、panic ではなく失敗の値になる

toggle の「t.items[i].done を書き換える」も同じ形になります。index_mut が、借りた要素と一緒に「書き換えた要素を元の列に戻す関数」（index_mut_back）を返します。論文では、この戻す関数を backward function と呼んでいます。

第0章のソートも同じです。&mut [u32] をその場で並べ替える関数は、「新しい Slice を返す」関数として表されました。

翻訳の限界と、信頼している部分

Rust なら何でも翻訳できるわけではありません。この book で踏んだものと、Aeneas の README にある制約です。

  • 中身を知らない標準ライブラリ：Aeneas が Lean でモデルを手書きした関数だけ、動きが分かります。std::mem::take はモデルが無く axiom になったので、std::mem::replace(&mut v, Vec::new()) に書き換えました（第1章）。
  • ループの書き方：README によると、入れ子のループの中の return と、外側のループへの break／continue はまだ扱えません。本編の中核は while と for を素直に書いています。
  • unsafe と並行処理：README では未対応です。論文も、内部可変性（RefCell など）と unsafe を使わない Rust を対象にしています。

翻訳できたあとも、証明の外に残る部分があります。ソートの README では次を「証明していない層」として挙げました。todo も同じです。

  • Charon が読む rustc と、実際にビルドする rustc。その先の LLVM のコード生成
  • Charon／Aeneas の翻訳器そのもの
  • Aeneas が手書きした標準ライブラリのモデル（ソートでは swap と添字、todo では Vec の push など）
  • Lean のカーネル
ポイント「Rust と相性がよい」は「Rust なら全部証明できる」ではありません。別名の無い、safe な、小さい関数なら、手で Lean に書き直さずに済む、という意味です。

JavaScript はどこが難しいか

JavaScript には、Rust の借用検査に当たる仕組みがありません。証明しにくい理由を並べます。

性質証明で困ること
オブジェクトの共有と書き換えどの変数も同じオブジェクトを指せる。a.done = true で、別の名前から見た値も変わる。「新しい値を返す」に直すには、誰が何を指しているかを全部追う必要がある
動的な型引数に何が来るかは実行するまで分からない。TypeScript の型は実行時には消え、as で外せる
暗黙の型変換== や + が、値の種類によって違う規則で動く
例外どの呼び出しも投げうる。投げたかどうかが型に出ない
非同期とイベントループawait のたびに、ほかの処理が割り込める。結果は実行順で変わる
外界の APIlocalStorage・fetch・タイマー・DOM。どれも Lean の外にあり、動きを誰かがモデルにする必要がある

この book で調べた範囲では、Aeneas のように JavaScript のコードをそのまま Lean に翻訳して証明する、実用段階の道具は見つけられませんでした。

だから付録F は MBT、付録D はモデル検査にした

付録F の reduce は、書き換えをせず新しい状態を返すように、わざと純粋に書きました。スプレッド構文（...）でコピーを作り、元の state には触りません。

純粋なので、仕様から作った操作の列を流し、1歩ごとに Quint の状態と比べられます。ただし「純粋に書いた」ことは、人がそう書いただけです。Rust のようにコンパイラが保証してはいません。だから証明ではなく、実行列を流して突き合わせる MBT にしました。

付録D の sync.ts も中身は純粋な関数です。難しいのはそれを呼ぶ外側で、localStorage・fetch・setTimeout が絡みます。

付録D で見つけた不具合は、どれも「送信・失敗・遅れた応答・別のタブの操作がどの順に起きるか」で起きました。これはコードの1行ずつではなく、タイミングの組み合わせの問題です。そこでコードを翻訳するのをやめ、2つのタブとサーバの動きを手で TLA+ にモデル化しました。手で書いたモデルとコードがずれる危険は残ります。

ほかの道具

  • Rust 側：Verus（Rust のソースに事前・事後条件を書き SMT で検査）、Kani（テストのように書いたハーネスを有界に全部調べる）、hax（Rust を F*・Rocq や、Aeneas 経由で Lean などに翻訳）があります。
  • JavaScript を「書く」のではなく「出す」道：Dafny は、証明したコードを C#・Go・Python・Java・JavaScript に変換できます。JS のコードを証明するのではなく、証明した言語から JS を生成する道です。
  • 言語を揃えない道：認可ポリシーの言語 Cedar は、Lean で書いたモデルと証明を持ち、本番の Rust 実装とは乱択の差分テストで突き合わせています。仕様は Lean、実装は別の言語、という付録F と同じ形です。

実務での分け方

flowchart LR
  UI["外側（画面・HTTP・DB）: JS/TS のまま、テストで確かめる"] --> Core["核（権限・お金・状態遷移）: Rust の純粋な小さい関数"]
  Core --> Proof["Aeneas で Lean に翻訳し、仕様どおりと証明"]
  • 証明したいのは、壊れると困る小さい核です。権限の判定、金額の計算、状態の変え方などです。
  • 核は Rust で、&mut か値を受け取って値を返す関数にします。I/O・時刻・乱数は引数で渡し、中では触りません。
  • 外側の HTTP・DB・画面は JS/TS のままでかまいません。核を呼ぶ方法（WebAssembly、別プロセスの API など）は別に選びます。呼び出し部分は証明の外なので、テストで確かめます。
  • 核を Rust にできない場合は、付録F のように仕様と実装を突き合わせる方法があります。
落とし穴核を切り出しても、外側が核を正しく呼んでいるかは証明されません。第2章の認可でいえば、「操作したのは誰か」を外側が正しく渡すことは、証明の前提です。

まとめ

  • Lean の証明は、書き換えの無い純粋な関数を前提にしている
  • Rust は別名を型で禁じるので、Aeneas は &mut を「新しい値を返す」に自動で直せる
  • 翻訳には限界（モデルの無い標準ライブラリ、ループの書き方、unsafe）があり、翻訳器と rustc は信頼している
  • JavaScript は共有と書き換え・動的な型・非同期・外界の API が多く、コードをそのまま証明しにくい。だから付録F は MBT、付録D は手で書いたモデルの検査にした
  • 実務では、証明する核を Rust の小さい純粋な関数に切り出し、外側は JS/TS のままにする分け方がとれる

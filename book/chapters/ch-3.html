第3章 まとめ

本編（ソート・todo・認可）で分かったことを4つにまとめ、自分のコードで試す最初の一歩を決めます。

この章のゴール

  • 証明が何を保証し、何を保証しないかを言える
  • 「検査が何を見逃すか」をわざと壊して数える理由を説明できる
  • 自分のコードで最初に証明する部分を選べる
  • 実務のどこに向き、どこに向かないかを説明できる

本編で分かったこと

1. 証明は、テストが素通りするバグを止める

わざと壊した実装で、テストと証明を比べました。

章壊した数単体テストを素通りした例
第0章 ソート8通り7個目から先を並べない（テストの例が5個以下だった）
第1章 todo の4操作4通りid = 40億のときだけ消さない・切り替えが常に「完了」
第2章 認可4通り持ち主を確かめずに消す・ユーザー 0 だけ裏口がある

テストは思いついた場面しか見ませんが、証明は前提を満たすすべての状態・すべての入力について言います。逆に、証明が止まってもバグとは限りません（第0章の > を >= にした例は、証明の書き方が原因でした）。

2. 全部緑でも、わざと壊して見逃しを数える

変異テスト（第2章）で、わざと壊した版を検査が落とせるかを数えます。落とせなかった数が見逃しです。緑だけを見ても、検査が何も見ていないのか、本当に正しいのかは区別できません。

ポイント「証明できた」と言う前に、sorry と、翻訳結果の axiom が 0 件であることを確かめます。sorry が残ると Lean は証明が無くても通し、axiom になった関数は中身が無いので何も証明できません。

3. 穴は証明していない層に集まる

第1章で見つかった本物の穴5件は、すべて保存・コマンドの層と前提の出どころにあり、証明した中核には0件でした（題名の改行で保存ファイルが壊れる、など）。

  • 証明の前提（不変条件）は、外から読んだ状態では保証されないので、境界で検査する
  • 本人確認・画面・通信のように、正しいと信じて使っている部分（信頼の境界）を書き出す
  • lake build は Rust との対応を見ない。Rust を直したら翻訳からやり直す

4. 仕様に書いたことしか守らない

コマンド名が done なのに中身が切り替えでも、仕様どおりなので定理は何も言いませんでした。認可も「変わらない・見えない・触れない」の1つを書き忘れれば、その穴はどの定理にも引っかかりません。

落とし穴人がレビューするのは証明ではなく仕様と定理の文です。証明は Lean が確かめますが、「何を証明したか」が意図どおりかは人にしか分かりません。

本編の道具が向く場面

Lean ＋ Aeneas は「すべての入力」について言えますが、書く量が多めです（todo の中核 約120行に、仕様 約250行・証明 約450行）。だから、壊れると致命的な小さな核（認可・お金）に絞ります。Lean の文法の早見は付録A、Lean で動かす Web サーバーは付録B、Rust を選んだ理由は付録C です。同期や複数タブなら付録D、DB や HTTP まで含めて認可を証明したいなら付録E、小さな範囲を数秒で全部調べたいなら付録F を見てください。

実務への適用についての所感

本書の題材と、筆者がいつも書いている web アプリの実務を並べて考えた所感です。特定のプロジェクトの話ではなく一般論で、1日試した範囲での見立てです。

1. 全部ではなく、壊れると致命的な小さな核に絞る

公開されている実務の事例（AWS の Cedar、Microsoft の SymCrypt など）も、対象は認可・暗号・OS の境界のような小さな核です。アプリ全体を証明している例はほぼありません。本書の todo でも、中核 約120行に対して仕様と証明は約700行になりました。「この関数が間違うと事故になるか」で対象を選びます。

2. 入れるなら、設計しているとき

いちばん効くのは、新しい仕組み（排他・同期・権限のルールなど）を作る前です。実装より先に仕様を書けば、穴が設計の段階で見つかります。付録D では、テスト18件が緑の同期アプリから、操作が黙って消える不具合が3つ出ました。逆に、事故のあとにテストで厚く守られた既存の部品に後から足しても、新しく分かることは少なめです。費用に見合うかを先に考えます。

3. 実装の言語で、使える型が決まる

型見つかるもの見逃すもの向く言語
実装そのものを証明（Aeneas・Verus など）特定の入力でだけ起きるバグも含め、すべての入力仕様に書いていないこと、証明の外の層Rust
モデルを証明して、実装とは差分テスト（Cedar 方式）よくある形のずれ。速く大量に試せる特定の入力でだけ起きるバグ（100万件試しても出なかった）何でもよい
モデル検査（Quint・TLA+）並行・順番の組み合わせで起きる不具合調べる範囲の外（範囲を人が選ぶ）何でもよい（コードとは別にモデルを書く）

TypeScript や Python の web アプリでは、実装そのものの証明は現実的ではありません。下の2つの型（モデル＋差分テスト、モデル検査）が入口になります。

4. 向かない所もはっきりある

  • 画面の表示（列が消える・見出しが崩れる）は、画面を見て確かめる
  • 外部サービスの実際の挙動（遅延・API の解釈の違い）は、モデルの前提の外にあるので実測が要る
  • 要件がまだ決まっていない所。形式検証は書かれた仕様の中しか見ない
  • 運用の罠（0件を成功と読む、途中で切れたログを信じる）。罠が仕様の側に移るだけになる

5. 速くなったのは証明で、人の理解は速くなっていない

今は AI エージェントが証明やモデルを書く流れになっていて、本書でもほとんどの証明を AI が書きました。それでも「この仕様は意図どおりか」「前提は本当に成り立つか」を判断するのは人で、ここが律速になります。入れるときは、証明の手間よりも仕様と定理の文を人が読む時間を見積もります。

ポイント迷ったら、まず小さなモデル検査か差分テストから始めます。言語を選ばず、既存のテストの延長で入れられます。そこで「全部の入力について言いたい」核が見つかったら、その部分だけを Rust に切り出して証明します。

初心者の次の一歩

  1. 小さな純粋関数で1本証明する。第0章のソートのように、「結果が満たす性質」で仕様を書きます
  2. Rust の判断の部分だけを切り出す。保存や画面から離した関数を Aeneas で翻訳し、sorry と axiom が 0 件かを確かめます
  3. わざと壊す。1行変えて証明が止まらなければ、それが見逃しです
  4. 認可は3つの性質に分けて書く。変わらない・見えない・触れない
  5. 証明の外は境界で検査する。前提を読み込むたびに確かめます
やってみよう

本編の検査を流し、1行壊してもう一度流します。

(cd sort-aeneas/lean && lake build)
./todo-aeneas/build.sh

元に戻して通ることも確かめます。

用語集

形式検証
プログラムが決まりを守ることを、テストではなく数学的な方法で確かめること
仕様
プログラムが「何をすべきか」を書いたもの。人が先に書き、人がレビューする
実装
実際に動くプログラム。本編では Rust
証明
実装が仕様を満たすことを、すべての入力について示す手順。正しいかは Lean が確かめる
定理
証明した主張。「他人の todo は変わらない」など
Lean
定理証明支援系。証明が正しいかを機械が検査する
sorry
Lean で証明を省略した印。0 件であることを確かめる
公理（axiom）
定義なしに「ある」とみなす宣言。これに頼ると何も証明できないので、翻訳結果に 0 件であることを確かめる
Charon / Aeneas
Rust のコードを読み取り（Charon）、Lean の関数に自動翻訳する（Aeneas）道具
状態
ある瞬間のデータ全体（todo の一覧と次の id など）
不変条件
どの操作のあとも必ず成り立つ性質。「id が重複しない」など。本編の証明はこれを前提にする
ループ不変条件
ループを何周しても成り立つ性質。ループのある関数の証明で人が書く
panic・あふれ
Rust のプログラムが途中で止まること・数が型の上限を超えること。Aeneas の翻訳では失敗として扱われ、起きないことも証明する
変異テスト
わざと壊した版を作り、検査がそれを落とせるかを見るテスト
認可
その人がその操作をしてよいかの判断。本人確認（認証）とは別
IDOR
他人のデータの id を指定するだけで読めたり変えられたりする穴
信頼の境界
証明の外にあり、正しいと信じて使っている部分（翻訳ツール・本人確認・保存など）

まとめ

  • 証明は、テストが素通りするバグを止める。ただし前提を満たす範囲で、仕様に書いたことだけ
  • 全部緑でも、わざと壊して見逃しを数える。sorry と axiom は 0 件
  • 穴は証明していない層に集まる。信頼の境界を書き出し、前提は境界で検査する
  • 人がレビューするのは仕様と定理の文
  • 実務では、小さな核に絞り、設計しているときに入れる。言語によって使える型が変わる
  • 次の一歩は、小さな純粋関数を1本証明すること

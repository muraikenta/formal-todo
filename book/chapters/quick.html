5分で読む 形式検証入門ブック

この本の結論と、それを支える数字だけを1ページにまとめました。

テストは選んだ入力だけ。証明は全部の入力。ただし仕様に書いたことだけ。

仕様・実装・証明

形式検証は、プログラムが約束を守ることを、すべての場合について数学で確かめることです。役割は3つに分かれます。第0章のソートで見ます。

①仕様結果が満たすこと

「小さい順に並んでいる」かつ「入力の並べ替えである」の2つだけ。並べ方は書きません。人が実装を見ずに先に書きます。

②実装ふつうの Rust

挿入ソートの手順を書きます。翻訳ツール（Aeneas）が、証明できる形の関数に自動で写します。

③証明機械が検査する

「どんな入力でも、止まり、実行時エラーで落ちず（panic せず）、仕様を満たす」を証明支援の言語 Lean が一字一句検査します。間違った証明は通りません。

人が読むのは仕様と定理の文です。証明の手順は機械に任せ、本書でも大半は AI が書きました。仕様が間違っていれば、証明は間違ったことを保証します。だから仕様は小さい例で先に試します。本編は同じ3段で、todo の4操作（第1章）と認可（第2章）を証明します。

数字で見る

実装をわざと壊して検査が気づくかを数えた結果と、証明のあとに残った穴です。

8通りソートを壊した数。「7個目から先は並べない」「12345 だけ動かさない」はテスト（例6つ）を素通りし、証明が止めました（第0章）
3 / 4認可で持ち主の確認を外す壊し方のうち、単体テストを素通りした数。4つとも証明が止めました（第2章）
5件証明が通ったあとに見つかった本物の穴。すべて保存・コマンドの層と前提の出どころにあり、証明した中核には0件（第1章）
18件 → 3つテスト18件が緑の同期アプリから、TLA+ のモデル検査（全部の順番をたどる）で見つけた「操作が黙って消える」不具合（付録D）

テストは思いついた場面しか見ません。証明は前提を満たすすべての状態について言うので止まります。逆に、証明が止まってもバグとは限りません（証明の書き方が原因のこともあります）。

守ってくれること・くれないこと

守ってくれること（証明した中核で）

  • 前提を満たすすべての入力・すべての状態で、仕様どおりに動くこと
  • 長い入力や特定の値でだけ起きる、仕様に反するバグ
  • 他人の todo は変わらない・見えない・触れないこと
  • panic しないこと

守ってくれないこと

  • 仕様に書いていないこと。「並んでいる」だけだと [0, 0, 0] を返すソートが通る。コマンド名が done なのに中身が切り替え、も仕様どおりなので見逃す
  • 証明していない層（保存・画面・通信）
  • 本人確認。証明は「渡されたユーザーが正しいなら」まで
  • 前提が本当に成り立つか（ファイルから読んだ状態は境界で検査する）。翻訳ツールと Lean そのものは信頼している

実務で使うなら

  • 壊れると致命的な小さな核（認可・お金）に絞る。todo の中核 約120行に、仕様と証明は約700行かかりました
  • 判断の部分を、保存や画面から離した Rust の関数に切り出して証明する
  • 入れるなら設計しているとき。実装より先に仕様を書くと、穴が設計の段階で見つかります
  • 全部緑でも、わざと壊して見逃しを数える。証明の省略（sorry）と中身の無い宣言（axiom）が 0 件かを確かめる
  • 律速は、仕様と定理の文が意図どおりかを人が読む時間。証明の手間より先にそこを見積もる

次に読む

通して読むなら第0章から。Lean の書き方は付録A、実務の所感は第3章、TypeScript など Rust 以外の入口（モデル検査）は付録D・付録Fにあります。

5分で読む 形式検証入門ブック

形式検証を知らない web エンジニアのための、本1冊ぶんの話を9枚で。

ソートを壊しました。テストは全部緑のままでした。

テストは、選んだ入力しか見ていません

壊し方は「7個目から先は並べない」。テストの例は、どれも5個以下の長さでした。

緑は「その入力では動いた」だけ

形式検証は、全部の入力について機械に確かめさせます

選んだ例ではなく、すべての入力について数学で確かめます。守るべき約束を実装と別に書いたものが「仕様」です。

テスト

  • 人が思いついた入力を試す
  • 例に入っていないバグは素通り

形式検証

  • 前提を満たすすべての入力について言う
  • 証明が正しいかは機械が検査する

やることは「仕様・実装・証明」の3段です

ソートで通します。人が書くのは①と②、③の検査は機械です。

①仕様結果が満たすこと

「小さい順」かつ「入力の並べ替え」。実装より先に書く。

②実装ふつうの Rust

挿入ソート。翻訳ツールが証明できる形に写す。

③証明機械が検査

「どの入力でも止まり、異常終了せず、仕様を満たす」を Lean が確かめる。

テストが見逃した壊し方を、証明は止めました

実装をわざと壊して、テストと証明のどちらが気づくかを数えました。

8通りソートを壊した数。冒頭の「7個目から先」など2つはテスト（例6つ）を素通りし、証明が止めた
3 / 4他人の todo を守る確認を外した4通りのうち、テストを素通りした数。4つとも証明が止めた

ただし、証明は「仕様に書いたこと」しか守りません

仕様が「小さい順に並んでいる」だけなら、何を入れても [0, 0, 0] を返す実装が証明を通ります。だから仕様は小さい例で先に試します。

形式検証は、契約書どおりかを全ページ調べる監査。書き忘れた項目は対象外です

見つかった穴は、証明していない層にありました

todo の証明が通ったあと、別の目で探すと本物の穴が見つかりました。証明した中核には0件です。

5件すべて保存・コマンドの層か、証明の前提を誰が満たすかの所にありました（題名の改行で保存ファイルが壊れ、消した todo が復活する、など）

実務では、小さな核に絞って入れます

todo の中核 約120行に、仕様と証明は約700行。壊れると事故になる所から始めます。

  • 小さな核（認可・お金）の判断だけを切り出す
  • 入れるなら設計の段階で。テストが緑の同期アプリでも、操作が消える不具合が3つ出た（付録D）
  • 全部緑でも、わざと壊して見逃しを数える

証明は AI が書けても、仕様を読むのは人です

本書の証明はほとんど AI が書きました。それでも前提の外と、証明していない層（保存・画面・本人確認）は守られません。仕様が意図どおりかを人が読むことが、仕事として残ります。

テストは選んだ入力だけ。証明は全部の入力。ただし仕様に書いたことだけ。

通して読むなら第0章から。todo の証明は第1章、認可は第2章、実務の所感は第3章、TypeScript など Rust 以外の入口は付録D・付録Fです。

第0章 はじめに：形式検証ってなに？

形式検証が「何をしてくれて、何をしてくれないか」を、小さな関数 sum_to でつかみます。

この章のゴール

  • 「テストは選んだ入力だけ、形式検証は全部（ただし仕様に書いたことだけ）」を説明できる
  • 仕様・実装・証明を、それぞれ誰が書き、どう信じるかが分かる
  • この book の4つの todo と、各道具の「保証すること・しないこと」を見渡せる

テストで困ること

sum_to(10) が 55 になるテストが緑でも、言えるのは「10 で 55 が返った」ことだけです。テストは人が選んだ入力しか確かめません。

筆者の実験では、todo の「消す」操作を「id が 40億のときだけ消さない」ように壊しても、単体テストは全部通りました。

形式検証とは

形式検証とは、プログラムが約束を守ることを、数学の方法ですべての場合について確かめることです。この約束（何を返すべきか）を実装とは別に書いたものを仕様と呼びます。

ポイントテストは選んだ入力だけ。形式検証は全部の入力。ただし、確かめるのは仕様に書いたことだけです。

3つの役割：仕様・実装・証明

  • 仕様：何を返すべきか。人が、実装を見ずに先に書きます。
  • 実装：ふだんのプログラム（Rust・JavaScript・TypeScript）。
  • 証明：「実装は仕様どおり」という主張を、論理でつないだもの。その主張を定理と呼びます。機械が一字一句検査するので、間違った証明は通りません。
flowchart LR
  A["① 仕様（人が書く）"] --> C["③ 証明（機械が検査）"]
  B["② 実装（人 or AI が書く）"] --> C
  C --> D["前提を満たすすべての入力で 実装 ＝ 仕様"]

人が読むのは仕様と定理の主張（何を前提に何を言うか）です。手順は機械に任せます。

小さな例で3段を体験する

第2章の流れを眺めます。題材は「0 + 1 + … + n を返す」sum_to、道具は Lean（証明を書いて機械に検査させる言語）です。

  1. 仕様を書く

    「何を返すか」だけを書き、ループのことは書きません。Nat は上限もあふれもない数学の自然数です。

    ∑ i ∈ range (n + 1), i は「0 から n までを全部足す」の意味です。

  2. 仕様そのものを確かめる

    仕様が間違っていれば、間違った実装も証明を通ります。

    和を range n と書き間違えたら、1行目で止まりました。

  3. 実装を書く

    実装はふつうの Rust です。u32 は 0 から 232 − 1（約43億）までなので、大きすぎる答えはあふれます。

  4. 「実装 ＝ 仕様」を証明する

    Rust は Aeneas（第2章）が Lean の関数に自動で翻訳します。その翻訳結果が仕様と一致することを定理に書きます。

    読み方は「答えが u32 に収まるなら（h）、sum_to n は失敗せずに r を返し、それは Spec.sum と等しい」です。.val は u32 を自然数として取り出します。h のような条件を定理の前提と呼びます。

  5. わざと壊して、証明が止まるのを見る

    ループの「i を進める」と「足す」の2行を入れ替えると、sum_to 10 は 45 になり、仕様を変えなくても証明が通らなくなりました。

落とし穴この定理が言うのは「収まるなら仕様どおり」までです。収まらないときの失敗は証明していません。また、翻訳はあふれを「失敗」と扱いますが、Rust の既定の release ビルドは黙って折り返すので、あふれたときの動きは一致しません。
やってみようLean と、ビルド済みの Aeneas の Lean ライブラリ（lakefile.toml が相対パスで参照）があれば、証明が通るかを確かめられます。エラーも sorry（証明の省略）も出なければ成功です。 
cd lean-aeneas
lake build
初回は Mathlib（数学の定理集）のキャッシュ展開込みで、筆者の環境では2分ほどかかりました。翻訳の道具（Charon と Aeneas）は第2章で説明します。

テストとの違いをもう一度

add 関数に「a = 123456789, b = 1 のときだけ 0 を返す」バグを入れました。ランダムな入力で実装と見本の答えを比べる差分テストは、100万件を種を変えて3回流しても見逃し、証明は通りませんでした。

一方、todo には「コマンド名は done なのに、中身は完了と未完了の切り替え」という作りがありました。仕様どおりなので、定理は何も言いません。形式検証は契約書どおりかを全ページ調べる監査で、書き忘れた項目は対象外です。

この book で作る4つの todo

4種類の道具は、「全部」の範囲と守るものが違います。

章todo と道具保証すること保証しないこと
第1章 Quint で書いた仕様＋JavaScript のアプリ id 0〜3 の範囲で、たどり着ける 225,531 通りの状態（ある時点のデータ全体）をすべて調べ、仕様の決まりが破れないこと。仕様から作った実行列 200本 × 30歩 ＝ 6,000 歩で、アプリが仕様どおり動くこと 調べた範囲の外。実行列に出てこない動き。画面の層（クリックや日本語入力の変換確定など）
第2章 Rust の中核＋Lean の証明（Aeneas） 追加・切り替え・削除・未完了の件数の4操作が、前提（id が重複しない等）を満たすすべての状態で仕様どおりであること 画面と保存。仕様に書いていないこと。翻訳ツールと Lean そのものは信頼している
第3章 認可つき todo（Aeneas の認可版・h5i・Nyxis） 他人の todo は変わらない・見えない・触れないこと（h5i は 108 定理）。Nyxis は「ハンドラはポリシー（権限の決まり）の範囲を超えない」こと ログインした人が本人か。JSON・HTTP・SQL への変換など証明していない層。ポリシーそのものが意図どおりか
第4章 複数タブで同期する todo（TLA+） タブ2枚・todo 1〜2件などの範囲で、送信・失敗・リロードが「どの順に起きても」4つの性質が守られること（破れる順番があれば手順を示す） 範囲の外。モデルとコードのずれ（コードを変えたらモデルも直す）

第4章では、テスト18件が緑だった todo から、操作が黙って消える不具合を3つ見つけます。第5章では道具の選び方と、見逃しを数える方法をまとめます。

ポイント第1章から順に読んでください。Quint はすぐ反例（決まりが破れる具体的な手順）が出るので、入口に向いています。
落とし穴検査が全部緑でも、正しさの証明にはなりません。筆者の最初の版は、仕様を壊しても緑のままでした。各章で「わざと壊して、検査が止まるか」を確かめます。

まとめ

  • テストは選んだ入力だけ、形式検証は全部の入力を確かめる。ただし仕様に書いたことだけ
  • 仕様は人が先に書いて小さい例で確かめ、証明は機械が検査する
  • 定理には前提がある。前提の外と、証明していない層（画面・保存・本人確認など）は守られない
  • Quint → Lean と Rust → 認可 → TLA+ の順に、4つの todo で道具を使い分ける

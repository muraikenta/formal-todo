第0章 はじめに：形式検証ってなに？

形式検証が「何をしてくれて、何をしてくれないか」を、ソートの関数でつかみます。

この章のゴール

  • 「テストは選んだ入力だけ、形式検証は全部（ただし仕様に書いたことだけ）」を説明できる
  • 仕様・実装・証明を、それぞれ誰が書き、どう信じるかが分かる
  • この book の4つの todo と、各道具の「保証すること・しないこと」を見渡せる

テストで困ること

ソートのテストで [3, 1, 2] が [1, 2, 3] になっても、言えるのは「その入力でそうなった」ことだけです。テストは人が選んだ入力しか確かめません。

筆者の実験では、ソートを「7個目から先は並べない」ように壊しても、テストは全部通りました。テストの例はどれも5個以下の長さだったからです。

形式検証とは

形式検証とは、プログラムが約束を守ることを、数学の方法ですべての場合について確かめることです。この約束（何を返すべきか）を実装とは別に書いたものを仕様と呼びます。

ポイントテストは選んだ入力だけ。形式検証は全部の入力。ただし、確かめるのは仕様に書いたことだけです。

3つの役割：仕様・実装・証明

  • 仕様：何を返すべきか。人が、実装を見ずに先に書きます。
  • 実装：ふだんのプログラム（Rust・JavaScript・TypeScript）。
  • 証明：「実装は仕様どおり」という主張を、論理でつないだもの。その主張を定理と呼びます。機械が一字一句検査するので、間違った証明は通りません。
flowchart LR
  A["① 仕様（人が書く）"] --> C["③ 証明（機械が検査）"]
  B["② 実装（人 or AI が書く）"] --> C
  C --> D["前提を満たすすべての入力で 実装 ＝ 仕様"]

人が読むのは仕様と定理の主張（何を前提に何を言うか）です。手順は機械に任せます。

ソートで3段を体験する

第2章の流れを、ソートで眺めます。道具は Lean（証明を書いて機械に検査させる言語）です。ソートを選んだのは、仕様と実装がまったく違う形になるからです。

  1. 仕様を書く：「どう並べるか」ではなく「結果が満たすこと」

    並べ方（アルゴリズム）は書きません。並べ終わった結果が満たすことを2つだけ書きます。

    Sorted は「小さい順に並んでいる」、Perm は「入力の並べ替えである（要素を足しても消してもいない）」です。∧ は「かつ」。挿入ソートでもマージソートでも、正しいソートならこの2つを満たします。

  2. 仕様そのものを確かめる

    仕様が間違っていれば、間違った実装も証明を通ります。だから小さい例で仕様を試します。by decide は「Lean がその場で計算して確かめる」という指示です。

    ¬ は「〜ではない」。最後の例が大事です。「並んでいる」だけを仕様にすると、何を入れても [0, 0, 0] を返す実装が通ってしまいます。

  3. 実装を書く

    実装はふつうの Rust の挿入ソートで、「どう並べるか」の手順を書きます。

  4. 「実装は仕様を満たす」を証明する

    Rust は Aeneas（第2章）が Lean の関数に自動で翻訳します。その翻訳結果が仕様を満たすことを定理に書きます。

    読み方は「どんな入力 v でも、insertion_sort v は止まり、panic（Rust の実行時エラーでの異常終了。配列の範囲外アクセスなど）せずに v' を返し、v' は v をソートしたものである」です。nat は Rust の u32 の列を、仕様の自然数の列に読み替える関数です。

  5. わざと壊して、テストと証明を比べる

    実装を8通りに壊して、Rust のテスト（例6つ）と証明のどちらが気づくかを数えました。

    壊し方テスト証明
    大きい順に並べる落ちる止まる
    最後の1つを差し込まない落ちる止まる
    7個目から先は並べない通る（見逃す）止まる
    12345 だけは動かさない通る（見逃す）止まる

    表は8通りのうち4つです。長い入力や特定の値でだけ起きるバグは、テストの例に入っていなければ見つかりません。証明は全部の入力について言うので止まります。

落とし穴証明が止まっても、バグがあるとは限りません。「等しいときも入れ替える」（> を >= に）は正しいソートのままですが、最初の証明は止まりました。証明が元の書き方に寄りすぎていたためで、証明を直すと通りました。
やってみようLean と、ビルド済みの Aeneas の Lean ライブラリがあれば、証明が通るかを確かめられます。先に sort-aeneas/lean/lakefile.toml の path を、自分の Aeneas の backends/lean の場所に書き換えてください（筆者の環境の相対パスのままです）。エラーも sorry（証明の省略）も出なければ成功です。 
cd sort-aeneas/lean
lake build
初回は Mathlib（数学の定理集）の準備込みで、筆者の環境では3分ほどかかりました。翻訳の道具（Charon と Aeneas）は第2章で説明します。

仕様に書いていないことは守られない

手順2の [0, 0, 0] がその例です。ソートでは、2つの性質で答えがただ1つに決まることまで証明して（sortOf_unique）、書き忘れの穴をふさいであります。

一方、todo には「コマンド名は done なのに、中身は完了と未完了の切り替え」という作りがありました。仕様どおりなので、定理は何も言いません。形式検証は契約書どおりかを全ページ調べる監査で、書き忘れた項目は対象外です。

この book で作る4つの todo

4種類の道具は、「全部」の範囲と守るものが違います。

章todo と道具保証すること保証しないこと
第1章 Quint で書いた仕様＋JavaScript のアプリ id 0〜3 の範囲で、たどり着ける 225,531 通りの状態（ある時点のデータ全体）をすべて調べ、仕様の決まりが破れないこと。仕様から作った操作の列 200本 × 30歩 ＝ 6,000 歩で、アプリが仕様どおり動くこと 調べた範囲の外。実行列に出てこない動き。画面の層（クリックや日本語入力の変換確定など）
第2章 Rust の中核＋Lean の証明（Aeneas） 追加・切り替え・削除・未完了の件数の4操作が、前提（id が重複しない等）を満たすすべての状態で仕様どおりであること 画面と保存。仕様に書いていないこと。翻訳ツールと Lean そのものは信頼している
第3章 認可つき todo（Aeneas の認可版・h5i・Nyxis） 他人の todo は変わらない・見えない・触れないこと（h5i は 108 定理）。Nyxis は「ハンドラはポリシー（権限の決まり）の範囲を超えない」こと ログインした人が本人か。JSON・HTTP・SQL への変換など証明していない層。ポリシーそのものが意図どおりか
第4章 複数タブで同期する todo（TLA+） タブ2枚・todo 1〜2件などの範囲で、送信・失敗・リロードが「どの順に起きても」4つの性質が守られること（破れる順番があれば手順を示す） 範囲の外。モデルとコードのずれ（コードを変えたらモデルも直す）

第4章では、テスト18件が緑だった todo から、操作が黙って消える不具合を3つ見つけます。第5章では道具の選び方と、見逃しを数える方法をまとめます。

ポイント第1章から順に読んでください。Quint はすぐ反例（決まりが破れる具体的な手順）が出るので、入口に向いています。
落とし穴検査が全部緑でも、正しさの証明にはなりません。筆者の最初の版は、仕様を壊しても緑のままでした。各章で「わざと壊して、検査が止まるか」を確かめます。

まとめ

  • テストは選んだ入力だけ、形式検証は全部の入力を確かめる。ただし仕様に書いたことだけ
  • 仕様は人が先に書いて小さい例で確かめ、証明は機械が検査する
  • 定理には前提がある。前提の外と、証明していない層（画面・保存・本人確認など）は守られない
  • Quint → Lean と Rust → 認可 → TLA+ の順に、4つの todo で道具を使い分ける

第1章 Quint で todo の仕様を書いて、全部の状態を調べる

todo アプリの決まりを Quint で仕様に書き、起こりうる状態を機械に全部調べさせます。最後に、仕様から作った操作の列を JavaScript アプリに流して突き合わせます。

この章のゴール

  • todo アプリを「状態」と「操作」で書ける
  • 不変条件を書き、quint test / quint run / TLC で調べられる
  • わざと壊した仕様で、検査の強さを測れる（変異テスト）
  • 仕様から作った操作の列でアプリをテストする（MBT）流れが分かる
  • 検査が緑でも残る見逃しを4つ言える

題材と道具

題材は todo アプリで、操作は追加・完了の切り替え・削除・題名の編集・全部切り替え・完了済みを消すの6つです。

道具は Quint（クイント）です。システムの決まりを書く言語で、見た目は TypeScript に似ており、書いた仕様を実行も全状態の検査もできます。版は 0.34.0 です。

Quint で書くのはアプリではなく、アプリの決まりです。アプリは JavaScript で書き、後半の MBT でつなぎます。

flowchart LR
  S["仕様 todo.qnt"] --> T["quint test（具体例）"]
  S --> R["quint run（ランダム）"]
  S --> V["TLC（全状態）"]
  S --> G["トレース200本"]
  G --> M["mbt.mjs"]
  A["アプリ todo-core.mjs"] --> M

  1. ステップ1: 状態を書く

    アプリが覚えていることを 状態 と呼びます。todo の一覧と、次に振る id の2つです。Quint では var で宣言します。

    last… と prev… は検査用の記録で、ステップ7で使います。アプリの状態は todos と nextId だけです。

  2. ステップ2: 操作を書く

    状態を変える操作を action（アクション）と呼びます。todos' のように '（プライム）を付けた名前が操作後の値です。

    all { … } は「中の条件が全部成り立つ」です。nextId < MAX_ID は、調べる範囲を有限にするための上限です。

    record は直前の操作の記録、BUG はわざと間違えた版への切り替えです。INPUTS.get(raw) は生の入力を空白を取った題名に変える表で、Quint に trim が無いので表で渡します。

    最後に、1歩ごとに6つのどれかが起きると書きます。

    nondet は「この中のどれでもよい」、any { … } は「どれか1つが起きる」です。

    ポイント仕様は「この順に呼ぶ」手続きではなく、「どの状態からでも6つのどれかが起こりうる」という可能性の全体です。

  3. ステップ3: 不変条件を書く

    不変条件は、どの操作の後でも成り立ってほしい性質です。

    1つの状態を見れば言えるので、形の性質と呼びます。

  4. ステップ4: 具体例で動かす（quint test）

    まず具体的な操作の列で動きを確かめます。単体テストと同じ感覚です。

    .then(…) は「続けてこの操作」、.expect(…) は「最後にこれが成り立つ」です。2つ目は空白だけの題名が弾かれることを見ます。具体例は4本です。

    動かすときは、上限などの定数を埋めた版を選びます。

    やってみよう具体例4本を流します。 
    cd quint-todo
quint test todo.qnt --main=todo4

  5. ステップ5: ランダムに歩かせる（quint run）と、全部見る（TLC）

    quint run は最大30歩の列をランダムに1万本試し、不変条件が破れたらそこまでの列（反例）を見せます。

    ランダムでは通らない道が残るので、到達できる状態を1つ残らず調べる TLC も使います（この手法をモデル検査と呼びます）。

    やってみよう safety は shapeOk にステップ7の性質を足した不変条件です。 
    cd quint-todo
quint run todo.qnt --main=todo7 --invariant=safety --max-steps=30 --max-samples=10000
quint verify todo.qnt --main=todo4 --backend=tlc --invariant=safety

    TLC は id 0〜3 で 225,531 状態を調べ、違反なしでした。id を件数で振る間違いを入れた todo4_idFromLength では違反が出ます。

    ポイント全部調べられるのは範囲を小さく区切ったからです。「id 0〜3 で違反なし」は「何件でも大丈夫」ではありません。

  6. ステップ6: わざと壊した仕様で検査を試す（変異テスト）

    緑でも、検査が甘いだけかもしれません。わざと書き間違えた仕様を検査が見つけるかを数えるのが 変異テスト です。

    各行は「名前・元・書き換え後」です。いまの仕様は 20本中20本を検出します。

    やってみよう 
    cd quint-todo
node mutate-spec.mjs

  7. ステップ7: 前後の性質を足す

    形の性質だけの最初の版は、17本中16本を見逃しました。「全部消す」「何もしない」も形は保つからです。

    そこで操作の前後を比べる 前後の性質を足しました。

    「直前が toggle なら、対象の1件の done だけが反転する」と読みます。これで 20/20 になりました。

    ポイント操作ごとに「決まったところだけ変え、他には触らない」まで書いて、初めて操作の意味を書いたことになります。

  8. ステップ8: 仕様から作った列をアプリに流す（MBT）

    アプリの中身は画面から切り離した状態遷移の関数で、action 1つが case 1つに対応します。

    MBT（モデルベーステスト）は、仕様が出した操作の列をアプリに1歩ずつ流し、毎歩状態を比べるテストです。列は ITF トレースという JSON に書き出します。

    比べるのは todos・nextId と「残り N 件」です。トレースは seed を固定して200本作るので、毎回同じ列になります。

    sequenceDiagram
  participant Q as "Quint（todo7）"
  participant F as "ITF トレース"
  participant B as "mbt.mjs"
  participant A as "todo-core.mjs"
  Q->>F: "200本×30歩を書き出す"
  B->>F: "1歩読む（操作と引数）"
  B->>A: "reduce(state, action)"
  A-->>B: "アプリの次の状態"
  B->>B: "仕様の状態と比べる"

    6,000歩が全歩一致し、壊したアプリ（mutate.mjs）は 19本中19本を検出しました。

    やってみよう 
    cd quint-todo
./gen-traces.sh
node mbt.mjs
node mutate.mjs
    全部まとめて流すなら ./check.sh です（約2分）。
    落とし穴MBT は「アプリが仕様どおりか」しか見ないので、仕様とアプリが同じ間違いをしていれば全部緑です。

  9. ステップ9: 独立レビューで見つかった穴を塞ぐ

    全部緑だった最初の版にも、別の目のレビューで穴が9件見つかりました。主な型は4つです。

    • 形だけの不変条件: 壊した仕様17本中16本を通した（ステップ7）。
    • 前後の性質の不足: 「他には触らない」を操作ごとに書いて塞いだ。
    • 範囲: MBT も id 0〜3 だったため、「5件目以降を弾く」アプリを見逃した。いまは MBT を7件まで広げた。
    • 入力: 題名の候補が "milk" "eggs" "" だけで、「trim を外す」「小文字にする」がすり抜けた。いまは次の表を使う。

    MBT が「残り N 件」を比べていなかった穴も塞ぎました。

    1 から n までの和で上限判定の > MAX を >= MAX に間違えても、上限 255 では見逃します。和がちょうど 255 になる n が無いからで、253（＝1+…+22）なら反例が出ます。

    検査は網で、網の目（範囲と入力）を決めるのは人です。

    落とし穴TLC が保証するのは「書いた性質が、選んだ範囲と入力の中で成り立つ」ことだけです。画面の操作やタブ間の同期は対象外で、「IME 確定の Enter で編集まで確定する」「2タブで互いの追加を消す」などは MBT の外で見つかりました（同期は第4章）。

まとめ

  • Quint では、アプリを「状態（var）」と「操作（action）」で書き、nondet で「どれでも起こりうる」を表す
  • quint test は具体例、quint run はランダム、TLC は小さな範囲の全状態（225,531 状態）を調べる
  • 「形の性質」だけでは弱い。「前後の性質」を足すと、壊した仕様 20/20 を検出できた
  • MBT で 6,000 歩をアプリに流して全歩一致。壊したアプリ 19/19 を検出
  • 通ったことより、何を見逃すかを数えるほうが大事。範囲・入力・比べる対象の選び方で見逃しが生まれる

第2章 Lean と Rust で「実装が仕様どおり」を証明する

この章では、Rust のコードが仕様どおりに動くことを証明します。

この章のゴール

  • 定理・証明・sorry を説明できる
  • 仕様を実装より先に書く理由が分かる
  • Rust が Charon と Aeneas で Lean に翻訳される流れが分かる
  • 「実装＝仕様」の定理の主張を読める
  • 証明が見つけるバグと、見逃すバグを知る

題材は第1章と同じ todo で、操作は4つです。

  • 足す（add）: 未完了の todo を末尾に足し、id を振る
  • 切り替える（toggle）: 完了と未完了を反転する
  • 消す（remove）: 指定した id の todo を除く
  • 未完了の件数（openCount）
ポイントコードにある user（操作した人）と owner（持ち主）は第3章「認可」で使います。この章では読み飛ばしてかまいません。

  S["仕様 Spec.lean（人が書く）"]
  R["Rust の中核 kernel/src/lib.rs"]
  C["Charon（Rust を読み取る）"]
  A["Aeneas（Lean に翻訳）"]
  K["翻訳結果 TodoKernel.lean"]
  P["証明 Proofs.lean"]
  R --> C --> A --> K

  K --> P

  1. Lean とは何か・定理と証明・sorry

    Lean はプログラミング言語であり、定理証明支援系（書いた証明が正しいかを機械が確かめる道具）でもあります。

    定理は「いつでも成り立つ」と主張する文です。例:「2回切り替えると元に戻る」。証明はその理由を書いたもので、足りないとビルドが通りません。テストと違い、すべての入力について言えます。

    sorry は「証明はあとで書く」という仮置きです。Lean は警告だけ出して定理を正しいと扱うので、完成前に 0 件を確かめます。

    やってみよう何も出なければ 0 件です。 
    cd todo-aeneas
grep -n sorry lean/*.lean

  2. 仕様 Spec.lean を先に書く（実装を見ない）

    最初に書くのは仕様です。実装を見てから書くと、実装のバグまで仕様に写してしまいます。

    todo 1件は id・持ち主・題名・完了の4つ。状態は todo のリストと「次に振る id」です。

    Nat は上限の無い自然数です。仕様は数学の数で書きます。

    操作は「状態を受け取り、新しい状態を返す関数」です。MaxId は id の上限（232−1）、empty は空の状態、Option Nat は「数がある（some）か無い（none）か」です。

    toggle は「当てはまる todo を全部反転する」と読みます。ループを書かず、map（全部を変換）と filter（条件で残す）で結果だけを言います。

    次に不変条件（どの操作のあとも状態が満たすべき約束）を書きます。

    ∧ は「かつ」、∀ t ∈ s.items は「どの todo t についても」、Nodup は「重複が無い」です。

    仕様の誤りは小さい例で確かめます。example は名前の無い定理、by decide は「計算して確かめて」です。

    使う人から見た性質も定理にします。

    読み方は「theorem 名前 (前提…) : 主張 := by 証明」です。(h : s.nextId ≠ MaxId) は「id を使い切っていないなら」という前提です。

    ポイント人が丁寧にレビューするのは Spec.lean だけです。仕様が間違っていれば、証明も間違ったことを保証します。

  3. Rust で中核を書く

    証明するのは状態を変える中核（kernel）だけで、画面と保存（CLI）は別のクレートに分けました。

    仕様は全部、Rust は最初の1件だけ反転します。一致するのは id が重複しないとき、つまり Inv の①が要ります。

  4. Aeneas で Rust を Lean に翻訳する（Charon → Aeneas）

    Lean は Rust を直接読めないので、2つの道具で翻訳します。

    • Charon: Rust のコンパイラの途中結果を読み、中間形式（.llbc）に書き出す
    • Aeneas: 中間形式を、意味を保って Lean の関数に翻訳する（翻訳の正しさは信頼する前提）

    build.sh が cargo test → charon → aeneas → lake build を順に流します。翻訳された add は次のとおりです。

    &mut Todos は「新しい Todos を返す」に変わり、戻り値は Result（ok か panic＝実行時エラーか）で包まれます。1#u32 の前の ← は「u32 の上限（約43億）を超えたら（あふれたら）ここで失敗」で、panic が見える形になります。

    落とし穴Aeneas は標準ライブラリを全部は知りません。std::mem::take は中身の無い宣言（axiom。定義なしに「ある」とみなす宣言）になり、何も証明できませんでした。std::mem::replace(&mut v, Vec::new()) に替え、翻訳後は grep axiom lean/TodoKernel.lean で 0 件を確かめます。

  5. 「実装＝仕様」を証明する（読み方を覚える）

    Rust の Todos を仕様の状態に読み替える関数 abs を決めます。

    示したいのは「どちら回りでも同じ」です。

    flowchart LR
  T["Rust の状態 t"] -- "Rust の add" --> T2["Rust の状態 t'"]
  T -- "abs で読み替え" --> S["仕様の状態"]
  T2 -- "abs で読み替え" --> X["同じになるはず"]
  S -- "Spec.add" --> X

    Lean で書くと add_correct です。

    • 前提 hinv: 今の状態が不変条件を満たすなら
    • Rust の add は panic せず、返り値 r と新しい状態 t' を返す
    • 返り値は仕様の add と同じ
    • 新しい状態を読み替えると、仕様の add の結果と同じ

    「panic しない」は、Inv から「件数は next_id 以下」（length_le_nextId）を導いて示しました。

    同じ形の定理を4操作に作りました（add_correct・toggle_correct・remove_correct・open_count_correct）。Inv を前提に取るのは、panic しないことを言う add と、id の重複が無いことが要る toggle です。

    証明本体は unfold・split・step・simp の組み合わせです。いまは主張（: と := by の間）だけ読めれば十分です。

    while のある関数では、ループ不変条件（1周ごとに保たれる約束。例:「i より前に探している id は無い」）を人が書きます。証明の手間の多くはここです。

    ポイント仕様の上で証明した性質（2回切り替えると元に戻る、など）は、「実装＝仕様」を通してそのまま Rust の性質になります。
    やってみよう最後の lake build（Lean のビルド）がエラー無しで終われば、4操作の「実装＝仕様」が確かめられています。 
    cd todo-aeneas
./build.sh

  6. わざと壊すと、証明が止まる

    証明がバグを捕まえるかは、Rust をわざと壊して確かめます。4通り試しました（認可を足す前の版）。

    壊し方（Rust）単体テスト証明
    toggle が反転でなく常に「完了」にする通る止まる（toggle_correct）
    remove が id = 40億 のときだけ消さない通る止まる（remove_correct）
    add が次の id を進めない落ちる止まる（add_correct）
    件数が完了済みも数える落ちる止まる（open_count_correct）

    上の2つは単体テストを素通りしました。テストは思いついた場面しか見ませんが、証明は全状態・全 id について言います。

    やってみようkernel/src/lib.rs の toggle にある t.items[i].done = !t.items[i].done; の右辺を true に変えて流します。cargo test は通り、toggle_correct で止まるはずです。確かめたら元に戻します。 
    cd todo-aeneas
./build.sh

  7. 証明していない層（保存・CLI）に穴があった

    証明が通ったあと、別の目で穴を探させると本物の穴が5件見つかりました。すべて「証明していない層」と「前提の出どころ」にあり、中核には無しでした。

    見つかった穴直し方
    題名に改行・タブを入れると保存ファイルが壊れ、消した todo が復活する題名の改行・タブを拒否。保存する前に「読み戻すと同じ状態になるか」を確かめる
    読めないファイルを空とみなし、list を1回打つだけで全件が消えるファイルが無いときだけ空から始め、それ以外は止める
    完了の列が 0/1 以外でも黙って未完了と読む0/1 以外は止める
    コマンド名が done なのに中身は切り替えで、2回打つと未完了に戻るコマンド名を toggle に
    add_correct の前提（Vec の長さが上限未満）を誰が満たすのか示していない前提を Inv に替え、そこから導いた

    4つ目のように、名前と中身のずれは仕様に無いので定理は何も言いません。

    toggle_correct の前提 Inv は、ファイルから読んだ状態では保証されないので、CLI が読むたびに検査します。

    落とし穴証明は仕様に書いたことしか守りません。外の層は境界で検査します。「Aeneas の Vec のモデルが本物と同じ」（メモリ不足は扱わない）も残る前提です。lake build は Rust との対応を見ないので、Rust を直したら build.sh を流し直します。

手間の目安（認可を足したあと）は、中核 約120行・仕様 約250行・証明 約450行です。だから証明は小さな中核に絞ります。

まとめ

  • Lean は証明を機械が確かめる道具。sorry 0 件でビルドが通って初めて「証明できた」
  • 仕様は実装を見ずに先に書き、小さい例と性質の証明で確かめる
  • Rust は Charon → Aeneas で Lean に翻訳され、panic の可能性は Result で見える
  • 「Rust で操作して読み替え ＝ 読み替えて仕様で操作」を4操作で証明。add と toggle は Inv が前提
  • わざと壊した4通りはすべて証明が止まり、うち2つは単体テストを素通りした
  • 本物の穴5件は、すべて証明していない層と前提の出どころにあった

第3章 認可を証明する：他人の todo には触れない

「アリスの todo はボブには変えられない・見えない」を、全ユーザー・全 id・全状態について証明します。道具は Aeneas・h5i・Nyxis の3つです。

この章のゴール

  • 認可を「変わらない・見えない・触れない」の3文で書ける
  • 仕様の上の認可を Rust に持ち上げる流れが分かる
  • 「悪いことが起きない」だけでは足りない理由が分かる
  • Nyxis で人が承認するものが分かる
  • 本人確認が証明の外に残ることを説明できる

認可とは

認可は「この人はこの操作をしてよいか」を決めることです。本人確認（認証・ログイン）は「本当にアリスか」を確かめることで、別物です。

よくある事故が IDOR（id を書き換えると他人のデータに届く不具合）です。/todos/42 を 43 に変えたら他人の todo が消えた、という種類で、これが認可の判断で起きないことを示します。

第2章の todo には、すでに持ち主（owner。作った人）が入っています。

  1. ステップ1: 認可の性質を言葉にする

    まず守りたいことを日本語で書きます。

    1. 変わらない: A が足す・切り替える・消すのどれをしても、B の持ち物は1件も変わらない
    2. 見えない: A に見せる id は、ちょうど「A が持ち主の todo の id」
    3. 触れない: 他人の id を指定すると、失敗を返し、状態はそのまま

    「変わらない」だけでは読む穴を、「見えない」だけでは消す穴を見逃すので、3つに分けます。

    ポイント証明は仕様に書いたことしか守りません。性質を1つ書き忘れたら、その穴はどの定理にも引っかかりません。

  2. ステップ2: 仕様に持ち主を入れる（Aeneas 版）

    第2章の Spec.lean で読み飛ばした持ち主の部分です。u は操作した人です。

    さらに ownedBy（u の todo だけのリスト）と、その id の一覧 visible を定義します。

  3. ステップ3: 3つの性質を定理として書く

    ステップ1の3文を定理にします。

    • add_others: u ≠ v なら、u が足しても v の持ち物は同じ（変わらない）。toggle_others・remove_others も同じ形
    • visible_iff: x が u に見える ⇔ x は u の todo の id（見えない）。「⇔」なので過不足がない
    • toggle_foreign: id 番の todo の持ち主が u でなければ「失敗・状態そのまま」（触れない）

    (h : Inv s) は第2章の不変条件（id が重複しない など）です。id が重複すると、同じ id の自分の todo と他人の todo が並びうるからです。

  4. ステップ4: Rust の実装に持ち上げる

    第2章で「実装＝仕様」（toggle_correct など）を証明済みなので、仕様の定理をそのまま Rust の定理に言い換えられます。

    最後の行で仕様の定理 Spec.toggle_others を使っています。Rust のループ相手に証明し直す必要はありません。

    表1: 持ち主の確認をわざと外したとき（todo-aeneas/README.md より。*_loop_spec は各操作のループ部分の証明）
    壊し方（Rust 側）単体テスト証明
    remove が持ち主を確かめない通る止まる（remove_loop_spec）
    remove でユーザー 0 だけは他人の todo も消せる（裏口）通る止まる（remove_loop_spec）
    一覧に id 1000 以上の他人の todo も混ざる通る止まる（visible_ids_loop_spec）
    toggle が持ち主を確かめない落ちる止まる（toggle_correct）

    単体テストは「ボブはアリスの todo を切り替えられない」場面しか見ないので、残りの穴を素通りします。

    やってみよう

    kernel/src/lib.rs の remove の条件 item.id == id && item.owner == user から && item.owner == user を消して流し直し、証明が止まるのを見たら戻します。

    cd todo-aeneas
./build.sh

  5. ステップ5: 「悪いことが起きない」だけでは足りない

    ステップ3の定理は「起きてはいけないことが起きない」という安全性です。何でも断るカーネルでも、安全性の定理はすべて通ってしまいます。

    ここからのコードは h5i 版（ステップ6）です。Principal は操作した人、Snapshot は状態、transition はコマンドを処理する関数です。

    落とし穴「改名で新しいタイトルを無視する」「完了フラグを勝手に戻す」カーネルも通ります。h5i 版の最初の版はこの状態で、レビューで指摘されました。

    そこで2種類の定理を足します。

    • やったことの中身（*_effect）: 成功したコマンドが何を残し、何を返すか
    • 成功する（*_ok）: 持ち主の正しい操作は必ず成功する

    「持ち主で（ho）、todo があれば（hq）、SetDone は成功する」と読みます。

    確かめ方は第1章の変異テスト（わざと壊したカーネルを検査が落とせるかを見る）です。

    改名が古いタイトルを残す壊し方で、「中身」の定理で初めて捕まります。

  6. ステップ6: h5i で DB と HTTP まで付ける

    h5i は Rust の web フレームワークです。判断をカーネル（DB・時計・通信に触らない純粋な関数）に集め、Aeneas で証明します。サーバは受け渡しだけです。

    返す書き込み1つ1つが許されるかは、仕様の allowed で定めます。

    主な定理です（h5i app check で 108 定理、sorry なし。公理は Lean 標準の3つだけで、第5章で触れます）。

    • authorized_reachable: 成功したコマンドの書き込みは本人の todo だけ
    • others_unchanged: 他人の todo は1件も変わらない
    • list_own: 一覧は本人の todo ちょうど
    • Effects.*_effect・Effects.*_ok: ステップ5の「中身」と「成功する」
    • Storage.db_inv: DB に書いて読み戻しても不変条件が保たれる
    落とし穴変異テストは 15/15 で検出しましたが、これは「どこかで止まった」数です。15 件とも止まったのは途中の補題（Commands.lean）で、主張が偽になったとは限りません。
    やってみよう

    証明と変異テストを流してサーバを起動し、「他人の todo を id 指定で触ってみる」欄で bob からアリスの todo を消してみます（Docker が要ります）。

    cd h5i-todo
h5i app prove . && h5i app mutate .
./run.sh

  7. ステップ7: Nyxis で「ポリシーとスキーマだけを人が承認する」

    Nyxis は Lean 製のバックエンドフレームワークです。人が承認するのは Cedar（認可のルールを書く言語）の2ファイルだけです。

    • スキーマ: データとアクションの定義。テーブル定義も兼ねる
    • ポリシー: 誰がどのアクションをしてよいか。書いていない操作はすべて拒否

    リクエストを処理するハンドラは AI に書かせてよい部分です。型の上で認可層にしか頼めず、DB に直接届きません。主体（操作している人）は JWT（ログインが発行する署名つきの札）から決まります。

    持ち主は principal から入るので、本文で偽っても効きません。

    lake build のたびに、「出された操作はすべて主体と一致し、ポリシーの範囲内」という定理が検査されます。

    本物のログイン（Supabase Auth）と DB を通す run.py check は 38 件通過しました。他人・匿名・偽や壊れた JWT での操作はすべて 403 で、DB は変わりません。

    認可層を迂回する試み2通りも、Lean のカーネル（証明を検査する部分。h5i のカーネルとは別物）とビルド時の監査（nyxis_check_app）が拒否しました。試したのはこの2通りだけです。

    落とし穴ポリシーを when { true }（誰でも何でもできる）にしても定理は通り、止めたのは #guard（具体例のテスト）10 本だけでした。ポリシーの中身は人とテストが見ます。

  8. ステップ8: 本人確認は証明の外

    どの道具も「本当にアリスか」は証明していません。

    • todo-aeneas: 環境変数 TODO_USER を信じるだけ
    • h5i 版: HMAC トークン（サーバが署名した札）と JSON の変換
    • Nyxis 版: HTTP・JWT・SQL への変換

    証明は「渡されたユーザーが正しいなら」までです。この境目を信頼の境界と呼びます。

    flowchart LR

第4章 TLA+ で同期を検査する：複数タブで操作が消える

オフラインでも動く todo アプリを2つのタブとサーバのモデルにして、送信・失敗・遅れた応答がどの順に起きても約束が守られるかを全部調べます。テストが全部緑のアプリから、操作が黙って消える不具合を3つ見つけます。

この章のゴール

  • 楽観的更新・送信待ち・再送・opId・version・seq の役割を説明できる
  • 同期の不具合がテストで見つかりにくい理由を「タイミングの組み合わせ」で説明できる
  • TLA+ で「状態」と「遷移」を書き、性質を不変条件として書ける
  • TLC の反例を、画面の操作の手順として読める
  • 「範囲」と「モデルに入れていない操作」が見逃しを生むことを、実例で知る

題材：同期つきの小さな todo アプリ

題材は todo/ フォルダの、Bun・TypeScript・SQLite で書いた web アプリです。追加・名前の変更・完了の切り替え・削除ができ、複数のタブや端末から同じ一覧を使えます。

回線が切れていても画面は動き、変更はつながったら送られます。この「あとで送る」部分を検査します。

  1. ステップ1：同期の仕組みを部品に分ける

    README の「同期の設計」にある部品は次の6つです。

    • 楽観的更新：サーバの返事を待たずに画面を変えること。画面には、サーバから最後に聞いた行（confirmed）に未確認の操作を当て直したものを出します。
    • 送信待ち（outbox）：サーバの確認がまだ来ていない操作の列。操作した順に並び、先頭から送ります。
    • 再送：失敗・タイムアウト（5秒）・応答の消失を区別せず、同じ操作をもう一度送ること。間隔は 0.5 秒から倍々、上限 10 秒です。
    • opId：操作ごとの名札で、形は クライアントID:連番。サーバは反映した opId を記録し、同じ opId は二度反映しません。
    • version：todo ごとの版の番号。変わるたびに 1 増え、手元より大きい行が届いたときだけ置き換えます。
    • seq：サーバ全体の通し番号。各行に最後に変わったときの seq が付きます。クライアントは取り込んだ位置（lastSeq）を覚え、2秒ごとにそれより新しい変更を取り込みます（pull）。

    クライアント ID はタブごとの保存場所 sessionStorage に置きます。送信待ちを含む状態全体は、ブラウザ全体で共有される localStorage に、クライアント ID ごとのキーで保存します。

    sequenceDiagram
  participant U as "ユーザー"
  participant T as "タブ"
  participant S as "サーバ"
  U->>T: "完了にする"
  T->>T: "opId c1:2 を送信待ちに積む・画面をすぐ変える"
  T->>S: "push（送信待ちの先頭から）"
  S-->>T: "応答が消える"
  T->>S: "同じ c1:2 を再送"
  S->>S: "c1:2 は反映済みなので二重にしない"
  S-->>T: "results に c1:2"
  T->>T: "送信待ちから c1:2 を外す"
  T->>S: "pull（lastSeq より新しい変更）"
  S-->>T: "変更された行と seq"
    ポイントこの設計の要は「opId が同じなら同じ操作」という約束です。サーバは opId だけで再送か新しい操作かを決めます。

  2. ステップ2：なぜテストでは見つかりにくいのか

    このアプリのテスト 18 件は全部緑です。再送、2台の同時編集、削除と編集の競合、オフラインからの復帰まで試しています。

    それでも、テストは書いた順番しか試しません。同期では次の出来事がどの順にも起きます。

    • タブ1で操作する・タブ2で操作する
    • 送る・送る前に失敗する・サーバに届く・応答が届く・タイムアウトで諦める
    • pull する・pull の応答が届く
    • リロードする・タブを複製する・タブを閉じる

    タブ2つでも、並べ方は人が書き切れない数になります。テストが鍵を数本試すことなら、これから使う道具はありうる鍵を全部試すことです。

  3. ステップ3：TLA+ で「状態」を書く

    TLA+ は、システムを「状態」と「遷移」で書く仕様の言語です。第1章の Quint は、TLA+ の考え方を読みやすい文法にしたものです。第1章で使った TLC は TLA+ のモデル検査器で、遷移を全部の順番でたどります。

    モデル todo/verification/SyncTodo.tla では、まず状態を変数で書きます。タブごとの値は「タブ → 値」の対応で持ちます。

    コメントに対応するコードの名前があります。モデルはコードを読まないので、この対応は人が付けています。

    コードに無い変数はゴースト変数で、性質を書くためだけの記録です。made はユーザーが積んだ操作の全部、acked は確認が来て送信待ちから外した操作です。

  4. ステップ4：TLA+ で「遷移」を書く

    遷移1つをアクションと呼びます。x' は次の状態での x、/\ は「かつ」、UNCHANGED は変わらない変数です。[pushing EXCEPT ![t] = n] は「タブ t の値だけを n に替えたもの」です。

    区切り方は「await を挟まない1区間を1アクションにする」です。JavaScript は1スレッドなので、その区間には何も割り込みません。await の前後は分け、間に何が起きてもよいようにします。

    送信の始まりでは、送信中でなく送信待ちが空でなければ、先頭から最大 50 件を送ります。

    失敗やタイムアウトは「諦める」アクションです。送信中の印を外すだけで送信待ちは残るので、次の送信で同じ opId のまま再送されます。

    タブの複製もアクションです。ブラウザの仕様で sessionStorage が写るので、複製したタブは同じクライアント ID になり、localStorage の同じキーから状態を読みます。

    最後に、ありうる遷移を「または（\/）」でつなぎます。\E t \in Tabs : … は「どれかのタブ t で」（第1章の nondet にあたる）、Spec は「Init から始めて毎歩 Next のどれかが起きる」という決まり文句です。

  5. ステップ5：守ってほしい4つの性質を書く

    性質は不変条件（どの状態でも成り立ってほしい条件）で書き、TLC がたどった全状態で確かめます。

    • AckedMeansApplied：送信待ちから外した操作は、その操作としてサーバに反映されている。破れると、変更が黙って消えたまま「同期済み」と出ます。
    • ClientOrderKept：同じクライアント ID の操作は、サーバで連番の順に1回ずつ処理される。破れると、遅れた古い再送が新しい値を巻き戻します。
    • Converged：送信待ちも途中の要求も無く全タブが pull し終えたら、全タブの一覧がサーバと同じ。破れると、タブごとに違う一覧が直りません。
    • NoOpLost：積んだ操作は、サーバに反映済みか、開いているタブの送信待ちか、途中の要求にある。破れると、操作がどこからも送られなくなります。
    ポイント4つとも「どう守るか」ではなく「何が守られていればよいか」を書いています。仕様を実装の都合から切り離すためです。

  6. ステップ6：範囲を決めて TLC で全部たどる

    全部たどるには世界を有限にします。設定ファイル（.cfg）で、todo 1件・名前2種類・各タブの操作2回・push 合計3回までに絞ります。2枚目のタブを「同じ URL を別タブで開く」か「複製する」かもここで選びます。

    この設定では4つとも成り立ちます（1,499,907 状態・1ワーカーで約 90 秒）。設定は6つあり、入れる操作が違います。

    • SyncTodo.cfg：別タブで同じ URL を開く・リロードあり・todo 1件。4つとも成り立つ
    • SyncTodoTwoTodos.cfg：同じで todo 2件・push 2回まで。4つとも成り立つ（651,021 状態・約 40 秒）
    • SyncTodoDuplicateTab.cfg：タブの複製。AckedMeansApplied と NoOpLost が破れる
    • SyncTodoDuplicateReload.cfg：複製＋リロード。NoOpLost と AckedMeansApplied が破れる
    • SyncTodoCloseTab.cfg：タブを閉じる。NoOpLost が破れる
    • SyncTodoStaleUI.cfg：編集中で描き直しが止まった古い画面からの操作も加えた版。4つとも成り立つ（16,004,587 状態。重いので任意）
    やってみようTLC は、pstack（AI エージェント向けのスキル集）の statechart スクリプトから呼びます。反例を「タブ1・タブ2・サーバ」の言葉の手順に直してくれます（view.mjs）。todo/ フォルダで、S にスクリプトのパスを入れて5つの設定を回します。初回は TLC と Java を入れるのでネットワークが要ります。 
    S=<pstack の skills/statechart/scripts/statechart のパス>
V=verification; O=$(mktemp -d)
for c in SyncTodo SyncTodoTwoTodos SyncTodoDuplicateTab SyncTodoDuplicateReload SyncTodoCloseTab; do
  echo "=== $c"; "$S" "$V/SyncTodo.tla" --config "$V/$c.cfg" --view "$V/view.mjs" --out "$O/$c"
done
    SyncTodo と SyncTodoTwoTodos の報告の「Rules that hold」に4つ並べば正常です。残り3つは破れるのが今の正常です。

  7. ステップ7：反例を手順として読む（発見1 タブの複製）

    性質が破れると、TLC はそこに至る最短の手順、つまり反例を出します。反例はそのまま再現手順です。

    SyncTodoDuplicateTab.cfg では AckedMeansApplied が 9 ステップで破れます。画面の言葉にすると次のとおりです。

    1. タブ1で todo「A」を追加する（op c1:1）
    2. タブを複製する。sessionStorage が写るので同じ ID c1、同じ状態（次の連番は 2）になる
    3. タブ1で名前を「B」に変える → op c1:2
    4. タブ2で完了にする → これも op c1:2
    5. 両方が送る。サーバは先に届いたタブ1の c1:2 を反映し、あとのタブ2の c1:2 を「再送」と見なして反映しない
    6. タブ2は応答に c1:2 があるので送信待ちから外し、「同期済み」と出る。サーバの todo は「B」未完了のまま
    flowchart LR
  A["タブ1 c1:2 名前をBに"] --> S["サーバ c1:2 を反映"]
  B["タブ2 c1:2 完了にする"] --> R["サーバ 反映済みの c1:2 と見なす"]
  R --> X["タブ2 送信待ちから外す・同期済みと表示"]
  X --> L["完了の操作が消える"]

    「opId が同じなら同じ操作」という約束が、複製で崩れました。重なったのが追加なら、その todo は作られず画面からも消えます。

  8. ステップ8：反例を読む（発見2 保存の上書き・発見3 タブを閉じる）

    発見2：複製したタブ同士が保存を上書きし合う。2つのタブは同じキー todo-state:c1 に保存するので、リロードすると最後に保存したもう一方のタブの状態を読みます。SyncTodoDuplicateReload.cfg で NoOpLost が 5 ステップで破れます。

    1. タブ1で追加する
    2. タブを複製する
    3. タブ1で名前を変える（c1:2 名前）
    4. タブ2で完了にする（c1:2 完了。保存が上書きされる）
    5. タブ1をリロードする → タブ1の送信待ちが「1:追加・2:完了」になり、名前の変更が消える

    発見3：送信待ちが残ったタブを閉じると、二度と送られない。ID はそのタブの sessionStorage にしか無く、開き直すと新しい ID になり、古いキーは誰も読みません。SyncTodoCloseTab.cfg で NoOpLost が 2 ステップで破れます。

    1. タブ1で追加する
    2. タブ1を閉じる

    反例はモデルの上の話なので、モデルの書き間違いもありえます。3つとも本物のコードで手順を流して再現し、本物の不具合と確かめました。

    ポイントREADME の「同じ URL を別タブで開くと別のクライアントになる」は複製で、「変更は送信待ちに残り、つながったら送られる」はタブを閉じると成り立ちません。検査は、設計書の言葉が破れる場面を手順で示しました。
    落とし穴「クライアント ID を起動ごとに作り直す」直し方は誤りです。リロードのたびに新しいキーを読み、発見3と同じ消失が毎回起きます。直したらモデルも同じ意味に直して回し直します。

  9. ステップ9：見逃しの形を知る

    最初の検証では SyncTodo.cfg が全部緑でも、不具合は残っていました。理由は2つです。

    1つ目：範囲が小さすぎると出ない不具合がある。todo 1件では push の応答の行がいつも最新版なので、「push の応答で lastSeq を進める」誤りは原理的に出ません。わざと入れて試すと、todo 1件では素通りし、SyncTodoTwoTodos.cfg で 11 ステップの反例が出ました。2件の設定はこのために足したものです。

    2つ目：モデルに無い操作は調べようがない。最初のモデルにはリロードとタブを閉じる操作が無く、監査で指摘されて足したら発見2と3が出ました。TLC は書かなかった遷移を一度もたどりません。

    落とし穴今のモデルにも無いもの：3枚目のタブや複製の複製、50 件を超える分割、pull のページ送り、localStorage への保存の失敗、「いつかは同期が済む」こと（活性）。コードを変えてもモデルは変わらないので、モデルを直さずに回した緑は何も示しません。
    やってみよう検査が働くかは、わざと壊して確かめます。SyncTodo.tla の SameOpId（いまは a.cid = b.cid /\ a.no = b.no）を a.no = b.no だけにして SyncTodo.cfg で回すと、別タブの連番 2 を取り違える 10 ステップの反例が出るはずです。確かめたら元に戻します。

まとめ

  • 同期は楽観的更新・送信待ち・再送・opId・version・seq の組み合わせで、要は「opId が同じなら同じ操作」
  • テストは書いた順番しか試さない。TLC は書いた遷移を全部の順番でたどる
  • 1アクションは「await を挟まない1区間」。性質は「何が守られていればよいか」を不変条件で書く
  • テスト 18 件が緑のアプリから、タブの複製・保存の上書き・タブを閉じる、で操作が消える不具合を3つ見つけ、本物のコードで再現した
  • 見逃しは「範囲が小さい」と「モデルに無い操作」から出る。検査はモデルに書いたことしか守らない

第5章 まとめ：どの道具をいつ使うか

第1〜4章の道具を比べ、場面ごとの選び方を決めます。最後に、「全部緑」でも残る見逃しの数え方をまとめます。

この章のゴール

  • 各道具が何を保証し、何を保証しないかを言える
  • 「検査が何を見逃すか」を先に数える理由を説明できる
  • 自分のアプリで最初に使う道具を決められる

道具の比較表

同じ todo アプリに当てた道具を並べます。数字は各章で測った値です。

道具（章）保証すること保証しないこと書く量反例が出るまで導入の重さ
Quint ＋ TLC ＋ MBT（第1章） 決めた小さな範囲（id 0〜3）の状態をすべて調べ、不変条件が破れない。MBT で、流した実行列（200本×30歩）の上ではアプリが仕様と同じ動きをする 範囲の外。仕様そのものの誤り（アプリに同じ誤りを入れれば MBT は緑） 仕様1ファイル＋突き合わせのスクリプト 数秒。バグ版は1歩目で破れる例もある。全網羅は 225,531 状態 軽い。TLC は quint verify --backend=tlc が自動で入れる
Lean ＋ Aeneas（第2〜3章） Rust の中核が、不変条件（id が重複しない など）を満たすすべての状態・すべての入力で仕様どおりに動く。他人の todo は変わらない 証明していない層（保存・コマンド名・画面）。本人確認 多い。Rust の中核 約120行に対し、仕様 約250行・証明 約450行 反例は出ない。証明が「止まる」だけ 重い。Rust・OCaml の道具・Aeneas のビルド。初回の lake build は Mathlib 込みで約2分
h5i（第3章） web アプリのカーネルの認可・他人不変・やったことの中身・panic しないこと。PostgreSQL の往復で不変条件が保たれる（108 定理） JSON の変換・トークン・テナントの切り分けなど、信頼している境界 カーネル1関数＋定理。手本のチュートリアルを真似る 反例は出ない。わざと壊したカーネル 15/15 を検出 中くらい。道具の版を h5i の指定に揃える（macOS 版リリースなら数分）。Docker の PostgreSQL
Nyxis（第3章） どんなリクエスト列でも、ハンドラはポリシーの権限を超えない ポリシーが意図どおりか（「誰でも何でも」にしても定理は通る）。入力の検証・業務ロジック 人が承認するのはスキーマとポリシーの2ファイル。ハンドラ（175 行）は AI に書かせてよい 反例は出ない。ポリシーの意図は #guard 37 本で確かめる 重い。初回ビルド約10分。依存が多い（libpq・Python 3.12・Supabase CLI・Docker）
TLA+ ＋ TLC（第4章） タブ2枚・決めた回数までの範囲で、出来事がどの順に起きても同期の4つの性質が守られる 範囲の外。モデルに書いていない出来事（最初はタブを閉じる・リロードが無かった）。モデルとコードのずれ モデル1ファイル＋設定ファイル（範囲ごとに1つ） 全網羅で約90秒（150万状態）。破れたら手順つきの反例が出る 中くらい。モデルはコードを読まないので、コードを変えたら人がモデルを直す
ポイントモデル検査（Quint・TLA+）は小さな範囲を全部見る道具で、速く、反例を手順で見せます。定理証明（Lean・h5i・Nyxis）はすべての入力について言えますが、書く量が多く、失敗しても「証明が止まった」としか分かりません。

実務では全部を証明せず、権限や暗号など壊れると致命的な小さい核に絞ります。モデルと本番は差分テスト（同じ入力を両方に入れて答えを比べる）でつなぐこともあります。

共通の教訓

道具は違っても、4つの章で同じ失敗が出ました。

1. 全部緑でも、見逃しを数える（わざと壊す）

第1章の最初の版は検査が全部緑でしたが、操作を間違えた仕様17本のうち16本を TLC が通しました。前後の性質を足すと 20/20 を検出しました。

h5i でも、何もしないカーネルが通りました。「持ち主の操作は必ず成功する」などを足して塞ぎました。

ポイント変異テスト（わざと壊した版を検査が落とせるかを見る）を仕様とアプリの両方に置きます。落とせなかった数が見逃しです。

2. 範囲の選び方で見逃す

  • > MAX を >= MAX に間違えても、MAX=255 では見逃しました。1+2+…+n が 255 になる n が無いからです
  • 第1章の MBT は id 0〜3 で「5件目で壊れる」を見逃しました
  • 第4章は todo 1件だと、todo をまたぐ不具合を素通りしました
落とし穴「1つの入力のときだけ 0 を返す」バグは、差分テスト 100万件 × 3 seed で見つかりませんでした。全網羅は小さく、ランダムは広く、致命的な核だけ証明します。

3. 証明していない層に穴が集まる

第2章の本物の穴5件は、すべて証明していない層と前提の出どころにありました（題名の改行で保存ファイルが壊れる、など）。第4章の不具合3つのうち2つも、モデルに「タブを閉じる」などを足して初めて出ました。

だから信頼している境界を書き出します。

4. 仕様に書いたことしか守らない

Nyxis でポリシーを「誰でも何でも」にしても定理は通り、止めたのは自分で書いた #guard でした。

落とし穴人がレビューするのは証明ではなく仕様と定理の文です。

初心者の次の一歩

  1. Quint から始める。数秒で反例が出ます
  2. わざと壊す。1行変えて検査が落ちなければ、それが見逃しです
  3. 同期や再送があるなら TLA+。順番の組み合わせはテストで書き切れません
  4. 認可やお金の核だけ Lean で証明する。新しく作るなら Nyxis や h5i に乗ります
やってみよう

検査を一式流し、1行壊してもう一度流します。

./quint-todo/check.sh
./todo-aeneas/build.sh
(cd h5i-todo && h5i app prove . && h5i app mutate .)

元に戻して緑に戻ることも確かめます。

第0章 はじめに：形式検証ってなに？

形式検証が「何をしてくれて、何をしてくれないか」を、ソートの関数でつかみます。

この章のゴール

  • 「テストは選んだ入力だけ、形式検証は全部（ただし仕様に書いたことだけ）」を説明できる
  • 仕様・実装・証明を、それぞれ誰が書き、どう信じるかが分かる
  • この book の構成（本編は Rust と Lean、付録でほかの道具）と、本編の各章が「保証すること・しないこと」を見渡せる

テストで困ること

ソートのテストで [3, 1, 2] が [1, 2, 3] になっても、言えるのは「その入力でそうなった」ことだけです。テストは人が選んだ入力しか確かめません。

筆者の実験では、ソートを「7個目から先は並べない」ように壊しても、テストは全部通りました。テストの例はどれも5個以下の長さだったからです。

形式検証とは

形式検証とは、プログラムが約束を守ることを、数学の方法ですべての場合について確かめることです。この約束（何を返すべきか）を実装とは別に書いたものを仕様と呼びます。

ポイントテストは選んだ入力だけ。形式検証は全部の入力。ただし、確かめるのは仕様に書いたことだけです。

3つの役割：仕様・実装・証明

  • 仕様：何を返すべきか。人が、実装を見ずに先に書きます。
  • 実装：ふだんのプログラム（Rust・JavaScript・TypeScript）。
  • 証明：「実装は仕様どおり」という主張を、論理でつないだもの。その主張を定理と呼びます。機械が一字一句検査するので、間違った証明は通りません。
flowchart LR
  A["① 仕様（人が書く）"] --> C["③ 証明（機械が検査）"]
  B["② 実装（人 or AI が書く）"] --> C
  C --> D["前提を満たすすべての入力で 実装 ＝ 仕様"]

人が読むのは仕様と定理の主張（何を前提に何を言うか）です。手順は機械に任せます。

ソートで3段を体験する

第1章の流れを、ソートで眺めます。道具は Lean（証明を書いて機械に検査させる言語）です。ソートを選んだのは、仕様と実装がまったく違う形になるからです。

  1. 仕様を書く：「どう並べるか」ではなく「結果が満たすこと」

    並べ方（アルゴリズム）は書きません。並べ終わった結果が満たすことを2つだけ書きます。

    Sorted は「小さい順に並んでいる」、Perm は「入力の並べ替えである（要素を足しても消してもいない）」です。∧ は「かつ」。挿入ソートでもマージソートでも、正しいソートならこの2つを満たします。Lean の書き方は付録A にまとめました。

  2. 仕様そのものを確かめる

    仕様が間違っていれば、間違った実装も証明を通ります。だから小さい例で仕様を試します。by decide は「Lean がその場で計算して確かめる」という指示です。

    ¬ は「〜ではない」。最後の例が大事です。「並んでいる」だけを仕様にすると、何を入れても [0, 0, 0] を返す実装が通ってしまいます。

  3. 実装を書く

    実装はふつうの Rust の挿入ソートで、「どう並べるか」の手順を書きます。

  4. 「実装は仕様を満たす」を証明する

    Rust は Aeneas（第1章）が Lean の関数に自動で翻訳します。その翻訳結果が仕様を満たすことを定理に書きます。

    読み方は「どんな入力 v でも、insertion_sort v は止まり、panic（Rust の実行時エラーでの異常終了。配列の範囲外アクセスなど）せずに v' を返し、v' は v をソートしたものである」です。nat は Rust の u32 の列を、仕様の自然数の列に読み替える関数です。

  5. わざと壊して、テストと証明を比べる

    実装を8通りに壊して、Rust のテスト（例6つ）と証明のどちらが気づくかを数えました。

    壊し方テスト証明
    大きい順に並べる落ちる止まる
    最後の1つを差し込まない落ちる止まる
    7個目から先は並べない通る（見逃す）止まる
    12345 だけは動かさない通る（見逃す）止まる

    表は8通りのうち4つです。長い入力や特定の値でだけ起きるバグは、テストの例に入っていなければ見つかりません。証明は全部の入力について言うので止まります。

落とし穴証明が止まっても、バグがあるとは限りません。「等しいときも入れ替える」（> を >= に）は正しいソートのままですが、最初の証明は止まりました。証明が元の書き方に寄りすぎていたためで、証明を直すと通りました。
やってみようLean と、ビルド済みの Aeneas の Lean ライブラリがあれば、lake build（Lean のビルド）で証明が通るかを確かめられます。先に sort-aeneas/lean/lakefile.toml の path を、自分の Aeneas の backends/lean の場所に書き換えてください（筆者の環境の相対パスのままです）。エラーも sorry（証明の省略）も出なければ成功です。 
cd sort-aeneas/lean
lake build
初回は Mathlib（数学の定理集）の準備込みで、筆者の環境では3分ほどかかりました。翻訳の道具（Charon と Aeneas）は第1章で説明します。

仕様に書いていないことは守られない

手順2の [0, 0, 0] がその例です。ソートでは、2つの性質で答えがただ1つに決まることまで証明して（sortOf_unique）、書き忘れの穴をふさいであります。

一方、todo には「コマンド名は done なのに、中身は完了と未完了の切り替え」という作りがありました。仕様どおりなので、定理は何も言いません。形式検証は契約書どおりかを全ページ調べる監査で、書き忘れた項目は対象外です。

第1章 Lean と Rust で todo が仕様どおりと証明する

第0章のソートと同じ「仕様 → 実装 → 証明」の3段を、今度は状態を持つ todo で通します。

この章のゴール

  • sorry が残っていると「証明できた」と言えない理由が分かる
  • 仕様を実装より先に書く理由が分かる
  • Rust が Charon と Aeneas で Lean に翻訳される流れが分かる
  • 「実装＝仕様」の定理の主張を読める
  • 証明が見つけるバグと、見逃すバグを知る

ソートは入力を受けて結果を返すだけでしたが、todo は操作のたびにデータが変わります。操作は4つです。

  • 足す（add）: 未完了の todo を末尾に足し、id を振る
  • 切り替える（toggle）: 完了と未完了を反転する
  • 消す（remove）: 指定した id の todo を除く
  • 未完了の件数（openCount）
ポイントコードにある user（操作した人）と owner（持ち主）は第2章「認可」で使います。この章では読み飛ばしてかまいません。
flowchart LR
  S["仕様 Spec.lean（人が書く）"]
  R["Rust の中核 kernel/src/lib.rs"]
  C["Charon（Rust を読み取る）"]
  A["Aeneas（Lean に翻訳）"]
  K["翻訳結果 TodoKernel.lean"]
  P["証明 Proofs.lean"]
  R --> C --> A --> K
  S --> P
  K --> P

  1. 証明の仮置き sorry

    第0章のとおり、Lean では定理（例:「2回切り替えると元に戻る」）を書き、その証明を機械が検査します。証明が足りないとビルドが通りません。

    sorry は「証明はあとで書く」という仮置きです。Lean は警告だけ出して定理を正しいと扱うので、完成前に 0 件を確かめます。

    やってみよう何も出なければ 0 件です。 
    cd todo-aeneas
grep -n sorry lean/*.lean

  2. 仕様 Spec.lean を先に書く（実装を見ない）

    最初に書くのは仕様です。実装を見てから書くと、実装のバグまで仕様に写してしまいます。

    todo 1件は id・持ち主・題名・完了の4つ。状態（ある時点のデータ全体）は todo のリストと「次に振る id」です。

    Nat は上限の無い自然数です。仕様は数学の数で書きます。

    操作は「状態を受け取り、新しい状態を返す関数」です。MaxId は id の上限（232−1）、empty は空の状態、Option Nat は「数がある（some）か無い（none）か」です。

    toggle は「当てはまる todo を全部反転する」と読みます。ループを書かず、map（全部を変換）と filter（条件で残す）で結果だけを言います。

    次に不変条件（どの操作のあとも状態が満たすべき約束）を書きます。

    ∧ は「かつ」、∀ t ∈ s.items は「どの todo t についても」、Nodup は「重複が無い」です。

    仕様の誤りは小さい例で確かめます。example は名前の無い定理、by decide は「計算して確かめて」です。

    使う人から見た性質も定理にします。

    読み方は「theorem 名前 (前提…) : 主張 := by 証明」です。(h : s.nextId ≠ MaxId) は「id を使い切っていないなら」という前提です。記号やタクティク（simp など）は付録A で引けます。

    ポイント人が丁寧にレビューするのは Spec.lean だけです。仕様が間違っていれば、証明も間違ったことを保証します。

  3. Rust で中核を書く

    証明するのは状態を変える中核（kernel）だけで、画面と保存（CLI）は別のクレートに分けました。なぜ Rust か（JavaScript ではなく）は付録C で説明します。

    仕様は全部、Rust は最初の1件だけ反転します。一致するのは id が重複しないとき、つまり Inv の①が要ります。

  4. Aeneas で Rust を Lean に翻訳する（Charon → Aeneas）

    Lean は Rust を直接読めないので、2つの道具で翻訳します。

    • Charon: Rust のコンパイラの途中結果を読み、中間形式（.llbc）に書き出す
    • Aeneas: 中間形式を、意味を保って Lean の関数に翻訳する（翻訳の正しさは信頼する前提）

    build.sh が cargo test → charon → aeneas → lake build を順に流します。翻訳された add は次のとおりです。

    このファイルは自動生成なのでコメントは足していません。上から「id を使い切っていたら何も変えずに返す」「末尾に足す」「next_id を1進める」で、Rust の add と1行ずつ対応します。&mut Todos は「新しい Todos を返す」に変わり、戻り値は Result（ok か panic＝実行時エラーか）で包まれます。1#u32 の前の ← は「u32 の上限（約43億）を超えたら（あふれたら）ここで失敗」で、panic が見える形になります。

    落とし穴Aeneas が中身を知っている標準ライブラリの関数は、Lean で動きを手書きしたモデルがあるものだけです。std::mem::take にはモデルがまだ無く、中身の無い宣言（axiom。定義なしに「ある」とみなす宣言）になって、何も証明できませんでした。std::mem::replace(&mut v, Vec::new()) に替え、翻訳後は grep axiom lean/TodoKernel.lean で 0 件を確かめます。

  5. 「実装＝仕様」を証明する（読み方を覚える）

    Rust の Todos を仕様の状態に読み替える関数 abs を決めます。

    示したいのは「どちら回りでも同じ」です。

    flowchart LR
  T["Rust の状態 t"] -- "Rust の add" --> T2["Rust の状態 t'"]
  T -- "abs で読み替え" --> S["仕様の状態"]
  T2 -- "abs で読み替え" --> X["同じになるはず"]
  S -- "Spec.add" --> X

    Lean で書くと add_correct です。

    「panic しない」は、Inv から「件数は next_id 以下」（length_le_nextId）を導いて示しました。

    同じ形の定理を4操作に作りました（add_correct・toggle_correct・remove_correct・open_count_correct）。Inv を前提に取るのは、panic しないことを言う add と、id の重複が無いことが要る toggle です。

    証明本体は unfold・split・step・simp の組み合わせです。いまは主張（: と := by の間）だけ読めれば十分です。

    while のある関数では、ループ不変条件（1周ごとに保たれる約束。例:「i より前に探している id は無い」）を人が書きます。証明の手間の多くはここです。

    ポイント仕様の上で証明した性質（2回切り替えると元に戻る、など）は、「実装＝仕様」を通してそのまま Rust の性質になります。
    やってみよう最後の lake build（Lean のビルド）がエラー無しで終われば、4操作の「実装＝仕様」が確かめられています。 
    cd todo-aeneas
./build.sh

  6. わざと壊すと、証明が止まる

    証明がバグを捕まえるかは、Rust をわざと壊して確かめます。4通り試しました（認可を足す前の版）。

    壊し方（Rust）単体テスト証明
    toggle が反転でなく常に「完了」にする通る止まる（toggle_correct）
    remove が id = 40億 のときだけ消さない通る止まる（remove_correct）
    add が次の id を進めない落ちる止まる（add_correct）
    件数が完了済みも数える落ちる止まる（open_count_correct）

    上の2つは単体テストを素通りしました。テストは思いついた場面しか見ませんが、証明は全状態・全 id について言います。

    やってみようkernel/src/lib.rs の toggle にある t.items[i].done = !t.items[i].done; の右辺を true に変えて流します。cargo test は通り、toggle_correct で止まるはずです。確かめたら元に戻します。 
    cd todo-aeneas
./build.sh

  7. 証明していない層（保存・CLI）に穴があった

    証明が通ったあと、別の目で穴を探させると本物の穴が5件見つかりました。すべて「証明していない層」と「前提の出どころ」にあり、中核には無しでした。

    見つかった穴直し方
    題名に改行・タブを入れると保存ファイルが壊れ、消した todo が復活する題名の改行・タブを拒否。保存する前に「読み戻すと同じ状態になるか」を確かめる
    読めないファイルを空とみなし、list を1回打つだけで全件が消えるファイルが無いときだけ空から始め、それ以外は止める
    完了の列が 0/1 以外でも黙って未完了と読む0/1 以外は止める
    コマンド名が done なのに中身は切り替えで、2回打つと未完了に戻るコマンド名を toggle に
    add_correct の前提（Vec の長さが上限未満）を誰が満たすのか示していない前提を Inv に替え、そこから導いた

    4つ目のように、名前と中身のずれは仕様に無いので定理は何も言いません。

    toggle_correct の前提 Inv は、ファイルから読んだ状態では保証されないので、CLI が読むたびに検査します。

    落とし穴「Aeneas の Vec のモデルが本物と同じ」（メモリ不足は扱わない）も残る前提です。lake build は Rust との対応を見ないので、Rust を直したら build.sh を流し直します。

手間の目安（認可を足したあと）は、中核 約120行・仕様 約250行・証明 約450行です。だから証明は小さな中核に絞ります。

まとめ

  • Lean は証明を機械が確かめる道具。sorry 0 件でビルドが通って初めて「証明できた」
  • 仕様は実装を見ずに先に書き、小さい例と性質の証明で確かめる
  • Rust は Charon → Aeneas で Lean に翻訳され、panic の可能性は Result で見える
  • 「Rust で操作して読み替え ＝ 読み替えて仕様で操作」を4操作で証明。add と toggle は Inv が前提
  • わざと壊した4通りはすべて証明が止まり、うち2つは単体テストを素通りした
  • 本物の穴5件は、すべて証明していない層と前提の出どころにあった

第2章 認可を証明する：他人の todo には触れない

「アリスの todo はボブには変えられない・見えない」を、全ユーザー・全 id・全状態について証明します。道具は第1章と同じ Lean と Aeneas です。

この章のゴール

  • 認可を「変わらない・見えない・触れない」の3文で書ける
  • 仕様の上の認可の定理を Rust に持ち上げる流れが分かる
  • 「悪いことが起きない」だけでは足りない理由が分かる
  • 本人確認が証明の外に残ることを説明できる

認可とは

認可は「この人はこの操作をしてよいか」を決めることです。本人確認（認証・ログイン）は「本当にアリスか」を確かめることで、別物です。

よくある事故が IDOR（id を書き換えると他人のデータに届く不具合）です。/todos/42 を 43 に変えたら他人の todo が消えた、という種類で、これが認可の判断で起きないことを示します。

第1章の todo には、すでに持ち主（owner。作った人）が入っています。

  1. 認可の性質を言葉にする

    まず守りたいことを日本語で書きます。

    1. 変わらない: A が足す・切り替える・消すのどれをしても、B の持ち物は1件も変わらない
    2. 見えない: A に見せる id は、ちょうど「A が持ち主の todo の id」
    3. 触れない: 他人の id を指定すると、失敗を返し、状態はそのまま

    「変わらない」だけでは読む穴を、「見えない」だけでは消す穴を見逃すので、3つに分けます。

    ポイント証明は仕様に書いたことしか守りません。性質を1つ書き忘れたら、その穴はどの定理にも引っかかりません。

  2. 仕様の持ち主の部分を読む

    第1章の Spec.lean で読み飛ばした持ち主の部分です。u は操作した人です。

    さらに ownedBy（u の todo だけのリスト）と、その id の一覧 visible を定義します。

  3. 3つの性質を定理として書く

    手順1の3文を定理にします。

    • add_others: u ≠ v なら、u が足しても v の持ち物は同じ（変わらない）。toggle_others・remove_others も同じ形
    • visible_iff: x が u に見える ⇔ x は u の todo の id（見えない）。「⇔」なので過不足がない
    • toggle_foreign: id 番の todo の持ち主が u でなければ「失敗・状態そのまま」（触れない）。remove_foreign も同じ形

    (h : Inv s) は第1章の不変条件（id が重複しない など）です。id が重複すると、同じ id の自分の todo と他人の todo が並びうるからです。

  4. Rust の実装に持ち上げる

    第1章で「実装＝仕様」（toggle_correct など）を証明済みなので、仕様の定理をそのまま Rust の定理に言い換えられます。

    仕様の定理を使うので、Rust のループ相手に証明し直す必要はありません。同じ形で add_others_rust などの「変わらない」と、一覧の visible_ids_only_own（見えない）も Rust の上で証明しています。

    第1章と同じく、Rust をわざと壊して証明が止まるかを確かめました。わざと壊したプログラムを検査が捕まえるかを数えるこのやり方を変異テストと呼びます。

    表1: 持ち主の確認をわざと外したとき（*_loop_spec は各操作のループ部分の証明）
    壊し方（Rust 側）単体テスト証明
    remove が持ち主を確かめない通る止まる（remove_loop_spec）
    remove でユーザー 0 だけは他人の todo も消せる（裏口）通る止まる（remove_loop_spec）
    一覧に id 1000 以上の他人の todo も混ざる通る止まる（visible_ids_loop_spec）
    toggle が持ち主を確かめない落ちる止まる（toggle_correct）

    単体テストは「ボブはアリスの todo を切り替えられない」場面しか見ないので、残りの穴を素通りします。

    やってみよう

    kernel/src/lib.rs の remove の条件 item.id == id && item.owner == user から && item.owner == user を消して流し直し、証明が止まるのを見たら戻します。

    cd todo-aeneas
./build.sh

  5. 「悪いことが起きない」だけでは足りない

    手順3の定理は「起きてはいけないことが起きない」という安全性です。何でも断る実装でも、安全性の定理はすべて通ってしまいます。「完了フラグを勝手に戻す」実装も、他人の todo に触れなければ通ります。

    これを防いでいるのは、第1章の「実装＝仕様」の定理です。持ち主の正しい操作は仕様どおりに効く、と言っているので、何もしない実装は toggle_correct で止まります。

    ポイント認可の定理は「やってはいけないこと」、実装＝仕様の定理は「頼んだことをやる」。両方そろって初めて、正しく動く認可になります。

  6. 本人確認は証明の外

    ここまでの証明は「本当にアリスか」を言っていません。todo-aeneas は環境変数 TODO_USER に書かれたユーザーを信じるだけです。

    証明は「渡されたユーザーが正しいなら」までです。この境目を信頼の境界と呼びます。

    flowchart LR
  A["利用者"] --> B["本人確認（TODO_USER）"]
  B --> D["認可の判断（Rust の中核）"]
  D --> E["保存ファイル"]
  subgraph 証明の外
    B
  end
  subgraph 証明した範囲
    D
  end
    ポイント定理の名前と一緒に「何を信じたか」を書き出します。証明は金庫で、鍵を誰に渡すかは金庫の外です。

    DB や HTTP、ログインまで含めた web アプリ全体を証明に載せる道具は付録Eで扱います。

まとめ

  • 認可は「変わらない・見えない・触れない」の3文に分けて定理にする
  • 「実装＝仕様」があれば、仕様の定理を Rust に持ち上げられる
  • 単体テストは思いついた場面しか見ない。証明は全ユーザー・全 id・全状態について言う
  • 安全性だけだと「何もしない実装」でも通る。「頼んだことをやる」定理と組にする
  • 本人確認は証明の外。何を信じたかを書き出す

第3章 まとめ

本編（ソート・todo・認可）で分かったことを4つにまとめ、自分のコードで試す最初の一歩を決めます。

この章のゴール

  • 証明が何を保証し、何を保証しないかを言える
  • 「検査が何を見逃すか」をわざと壊して数える理由を説明できる
  • 自分のコードで最初に証明する部分を選べる
  • 実務のどこに向き、どこに向かないかを説明できる

本編で分かったこと

1. 証明は、テストが素通りするバグを止める

わざと壊した実装で、テストと証明を比べました。

章壊した数単体テストを素通りした例
第0章 ソート8通り7個目から先を並べない（テストの例が5個以下だった）
第1章 todo の4操作4通りid = 40億のときだけ消さない・切り替えが常に「完了」
第2章 認可4通り持ち主を確かめずに消す・ユーザー 0 だけ裏口がある

テストは思いついた場面しか見ませんが、証明は前提を満たすすべての状態・すべての入力について言います。逆に、証明が止まってもバグとは限りません（第0章の > を >= にした例は、証明の書き方が原因でした）。

2. 全部緑でも、わざと壊して見逃しを数える

変異テスト（第2章）で、わざと壊した版を検査が落とせるかを数えます。落とせなかった数が見逃しです。緑だけを見ても、検査が何も見ていないのか、本当に正しいのかは区別できません。

ポイント「証明できた」と言う前に、sorry と、翻訳結果の axiom が 0 件であることを確かめます。sorry が残ると Lean は証明が無くても通し、axiom になった関数は中身が無いので何も証明できません。

3. 穴は証明していない層に集まる

第1章で見つかった本物の穴5件は、すべて保存・コマンドの層と前提の出どころにあり、証明した中核には0件でした（題名の改行で保存ファイルが壊れる、など）。

  • 証明の前提（不変条件）は、外から読んだ状態では保証されないので、境界で検査する
  • 本人確認・画面・通信のように、正しいと信じて使っている部分（信頼の境界）を書き出す
  • lake build は Rust との対応を見ない。Rust を直したら翻訳からやり直す

4. 仕様に書いたことしか守らない

コマンド名が done なのに中身が切り替えでも、仕様どおりなので定理は何も言いませんでした。認可も「変わらない・見えない・触れない」の1つを書き忘れれば、その穴はどの定理にも引っかかりません。

落とし穴人がレビューするのは証明ではなく仕様と定理の文です。証明は Lean が確かめますが、「何を証明したか」が意図どおりかは人にしか分かりません。

本編の道具が向く場面

Lean ＋ Aeneas は「すべての入力」について言えますが、書く量が多めです（todo の中核 約120行に、仕様 約250行・証明 約450行）。だから、壊れると致命的な小さな核（認可・お金）に絞ります。Lean の文法の早見は付録A、Lean で動かす Web サーバーは付録B、Rust を選んだ理由は付録C です。同期や複数タブなら付録D、DB や HTTP まで含めて認可を証明したいなら付録E、小さな範囲を数秒で全部調べたいなら付録F を見てください。

実務への適用についての所感

本書の題材と、筆者がいつも書いている web アプリの実務を並べて考えた所感です。特定のプロジェクトの話ではなく一般論で、1日試した範囲での見立てです。

1. 全部ではなく、壊れると致命的な小さな核に絞る

公開されている実務の事例（AWS の Cedar、Microsoft の SymCrypt など）も、対象は認可・暗号・OS の境界のような小さな核です。アプリ全体を証明している例はほぼありません。本書の todo でも、中核 約120行に対して仕様と証明は約700行になりました。「この関数が間違うと事故になるか」で対象を選びます。

2. 入れるなら、設計しているとき

いちばん効くのは、新しい仕組み（排他・同期・権限のルールなど）を作る前です。実装より先に仕様を書けば、穴が設計の段階で見つかります。付録D では、テスト18件が緑の同期アプリから、操作が黙って消える不具合が3つ出ました。逆に、事故のあとにテストで厚く守られた既存の部品に後から足しても、新しく分かることは少なめです。費用に見合うかを先に考えます。

3. 実装の言語で、使える型が決まる

型見つかるもの見逃すもの向く言語
実装そのものを証明（Aeneas・Verus など）特定の入力でだけ起きるバグも含め、すべての入力仕様に書いていないこと、証明の外の層Rust
モデルを証明して、実装とは差分テスト（Cedar 方式）よくある形のずれ。速く大量に試せる特定の入力でだけ起きるバグ（100万件試しても出なかった）何でもよい
モデル検査（Quint・TLA+）並行・順番の組み合わせで起きる不具合調べる範囲の外（範囲を人が選ぶ）何でもよい（コードとは別にモデルを書く）

TypeScript や Python の web アプリでは、実装そのものの証明は現実的ではありません。下の2つの型（モデル＋差分テスト、モデル検査）が入口になります。

4. 向かない所もはっきりある

  • 画面の表示（列が消える・見出しが崩れる）は、画面を見て確かめる
  • 外部サービスの実際の挙動（遅延・API の解釈の違い）は、モデルの前提の外にあるので実測が要る
  • 要件がまだ決まっていない所。形式検証は書かれた仕様の中しか見ない
  • 運用の罠（0件を成功と読む、途中で切れたログを信じる）。罠が仕様の側に移るだけになる

5. 速くなったのは証明で、人の理解は速くなっていない

今は AI エージェントが証明やモデルを書く流れになっていて、本書でもほとんどの証明を AI が書きました。それでも「この仕様は意図どおりか」「前提は本当に成り立つか」を判断するのは人で、ここが律速になります。入れるときは、証明の手間よりも仕様と定理の文を人が読む時間を見積もります。

ポイント迷ったら、まず小さなモデル検査か差分テストから始めます。言語を選ばず、既存のテストの延長で入れられます。そこで「全部の入力について言いたい」核が見つかったら、その部分だけを Rust に切り出して証明します。

初心者の次の一歩

  1. 小さな純粋関数で1本証明する。第0章のソートのように、「結果が満たす性質」で仕様を書きます
  2. Rust の判断の部分だけを切り出す。保存や画面から離した関数を Aeneas で翻訳し、sorry と axiom が 0 件かを確かめます
  3. わざと壊す。1行変えて証明が止まらなければ、それが見逃しです
  4. 認可は3つの性質に分けて書く。変わらない・見えない・触れない
  5. 証明の外は境界で検査する。前提を読み込むたびに確かめます
やってみよう

本編の検査を流し、1行壊してもう一度流します。

(cd sort-aeneas/lean && lake build)
./todo-aeneas/build.sh

元に戻して通ることも確かめます。

付録B Lean で Web サーバーも作れる

Lean は証明の道具だと思われがちですが、普通のプログラムも書けます。付録E の Nyxis は、HTTP サーバーそのものが Lean で動いています。この付録では、その仕組みと、どこまでが証明でどこからが信頼かを見ます。

この付録のゴール

  • Lean が実行ファイルを作る道筋（C へのコンパイル・IO・FFI・lake）が分かる
  • Nyxis でリクエストが DB に届くまでの道と、証明の範囲を区別できる
  • 「証明した言語でそのまま動かす」と「動かす言語から翻訳して証明する」を比べられる

Lean はプログラミング言語でもある

Lean の公式サイトは、Lean をプログラミング言語であり証明支援系と紹介しています。実行の仕組みは次の4つです。

  • C へのコンパイル: Lean のコードは C に変換され、C コンパイラでオブジェクトファイルになり、実行ファイルにリンクされます（Lake のリファレンス）。Lean の配布物には C のツールチェーンが入っています。
  • IO: ファイル・環境変数・ネットワークなどの副作用は IO 型の値として書きます。main も IO Unit を返す関数です。
  • FFI: @[extern "記号名"] を付けると、Lean の宣言が C の関数に結び付きます（FFI のリファレンス）。
  • lake: 標準のビルドツールです。依存の取得・ビルド・テストを受け持ちます。

HTTP サーバーも、Lean の標準ライブラリに Std.Http（HTTP/1.1 サーバーの実装）があります。Nyxis はこれを使っています。

  1. 起動は普通の main 関数

    Nyxis の todo の起動コードです。引数と環境変数を読み、サーバーを立てます。どの Web フレームワークにもある起動処理と同じ形です。

    実行ファイルは lakefile で宣言し、lake build で todoServer ができます。Nyxis はこのリポジトリと同じ階層に clone してビルドしておき、require で ../../../nyxis を指します。

  2. DB には FFI で C のライブラリを呼ぶ

    PostgreSQL への接続は、Lean で書き直していません。C のクライアント libpq を FFI で呼びます。Nyxis は lean-pq（libpq を Lean から呼ぶライブラリ）を、版を固定して取り込み、手を加えて使います。

    EIO LeanPq.Error Handle は「失敗すると LeanPq.Error を返し、成功すると接続 Handle を返す IO」、@& は「文字列を渡すだけで所有権は渡さない」という印です。opaque なので、Lean からは中身が見えません。中身は C 側の lean_pq_connect_db で、そこが libpq の PQconnectdb を呼びます。JWT の署名の検査も同じく、OpenSSL の libcrypto を FFI で使います。

    ポイントFFI の先は Lean のカーネルが検査しません。@[extern] を付けた宣言は「C 側がこの型どおりに動く」と信頼しているだけです。

  3. ハンドラは「頼みごとの列」というデータ

    ハンドラの型 Nyxis.Handler は IO ではありません。「値を返して終わる」か「アクションを呼び、結果を待って続ける」かの2通りしかないデータです。

    このデータを Nyxis が解釈し、call のたびに認可層で Cedar ポリシーを判定してから DB に届けます。ハンドラは DB にも IO にも直接届かないので、定理は「ハンドラが何を書いても」成り立ちます。

リクエストが DB に届くまで

緑が純粋なモデルで証明された部分、青が証明済みの接続コード、赤が信頼している接続コードと外部ライブラリです（Nyxis の ASSUMPTIONS.md の分け方を簡略化）。色の無いハンドラは、証明も信頼もしていない部分です。定理が「どんなハンドラでも」成り立つので、中身を問いません。

ビルドのたびに定理を検査する

付録E で見た authorization_safety は、アプリの Todo/Approved.lean にあります。lake build はコンパイルと同時に Lean のカーネルでこの証明を検査します。さらに起動コードは、使っている公理が標準の3つだけかをビルド時に確かめます。

ただし Lean そのものには、型の上では純粋に見せて実行時は別のことをする抜け道があります。@[implemented_by]（実行時だけ別の関数に差し替える）や unsafe です。Nyxis は、アプリの最上位モジュール Todo.lean の末尾に置いた nyxis_check_app で、アプリ側の全モジュールの宣言をビルド時に監査します。

アプリ側は @[extern] も使えません。FFI を使えるのは Nyxis の中の信頼された接続コードだけです。

やってみよう作業用のコピーで、ハンドラに @[implemented_by] で「型の上では純粋・実行時はファイルを読む」関数を入れて lake build します。Lean のカーネルは通しますが、nyxis_check_app が implemented_by attribute で止めます。普通の関数で unsafeBaseIO を使うと、こちらは Lean が拒否します。
落とし穴ポリシーを「誰でも何でもできる」に書き換えても、定理は通ります。定理が保証するのは「ハンドラがポリシーを超えない」ことで、ポリシーが意図どおりかではありません。そこは人の承認とテストの仕事です（付録E）。

h5i との違い

付録E の h5i は、サーバーもカーネル（判断を集めた純粋な関数。Lean のカーネルとは別物）も Rust です。Lean はカーネルを Aeneas で翻訳した先で、証明のためだけに使います。動いているのは Rust のプログラムです。Nyxis はサーバー自体が Lean で、証明した定義から作った実行ファイルがそのまま動きます。

付録C Lean は Rust と相性がよく、JavaScript とは相性が悪い

本編では todo の中核を Rust で書き、Lean に翻訳して証明しました。同じ todo でも、JavaScript／TypeScript 版（付録D・F）では証明をせず、MBT（モデルに基づくテスト。仕様から作った操作の列を実装に流して突き合わせる）とモデル検査にしました。この付録では、その分け方の理由を説明します。

この付録のゴール

  • Rust の所有権と借用があると、書き換えを「新しい値を返す」関数に直せる理由を説明できる
  • 翻訳の限界と、翻訳で信頼している部分を言える
  • JavaScript のコードを証明しにくい理由を、具体的なコードで説明できる
  • 証明する核を Rust に切り出し、外側は JS/TS のままにする分け方を説明できる

Lean の関数は書き換えをしない

Lean の関数は純粋な関数です。同じ引数なら同じ値を返し、引数を書き換えません。証明はこの性質に頼っています。「t に足したあとの t」を、普通の式として扱えるからです。

一方、実際のプログラムは値を書き換えます。証明するには、書き換えを「新しい値を返す」に置き換える必要があります。置き換えてよいのは、書き換えられる値を、ほかの誰も見ていないときだけです。誰かが同じ値を見ていると、その人から見た値も一緒に変わるので、「新しい値を返す」では表せません。同じ値を2つの名前から見ている状態を別名（エイリアス）と呼びます。

Rust は別名を型で禁じている

Rust の &mut（書き換えてよい借用）は、借りている間ほかの誰も同じ値を見られません。コンパイラがこれを検査します。だから Aeneas は、&mut Todos を受け取る関数を「Todos を受け取り、新しい Todos を返す」関数に直せます。メモリやアドレスを Lean で扱う必要がありません。Aeneas の論文 Aeneas: Rust Verification by Functional Translation（ICFP 2022）は、この考え方を「借用の規則に頼って、メモリの推論を要らなくする」と述べています。

本編の add を並べます。上が手で書いた Rust、下が Charon（Rust のコンパイラから中間表現を取り出す道具）→ Aeneas が自動で作った Lean です。

違いは3つです。

  • 引数の &mut Todos が、ただの Todos になった
  • 戻り値が「元の戻り値 × 新しい Todos」の組になった。書き換えた結果は、戻り値として外に出る
  • 全体が Result に包まれた。id + 1 のあふれや添字の範囲外は、panic ではなく失敗の値になる

toggle の「t.items[i].done を書き換える」も同じ形になります。index_mut が、借りた要素と一緒に「書き換えた要素を元の列に戻す関数」（index_mut_back）を返します。論文では、この戻す関数を backward function と呼んでいます。

第0章のソートも同じです。&mut [u32] をその場で並べ替える関数は、「新しい Slice を返す」関数として表されました。

翻訳の限界と、信頼している部分

Rust なら何でも翻訳できるわけではありません。この book で踏んだものと、Aeneas の README にある制約です。

  • 中身を知らない標準ライブラリ：Aeneas が Lean でモデルを手書きした関数だけ、動きが分かります。std::mem::take はモデルが無く axiom になったので、std::mem::replace(&mut v, Vec::new()) に書き換えました（第1章）。
  • ループの書き方：README によると、入れ子のループの中の return と、外側のループへの break／continue はまだ扱えません。本編の中核は while と for を素直に書いています。
  • unsafe と並行処理：README では未対応です。論文も、内部可変性（RefCell など）と unsafe を使わない Rust を対象にしています。

翻訳できたあとも、証明の外に残る部分があります。ソートの README では次を「証明していない層」として挙げました。todo も同じです。

  • Charon が読む rustc と、実際にビルドする rustc。その先の LLVM のコード生成
  • Charon／Aeneas の翻訳器そのもの
  • Aeneas が手書きした標準ライブラリのモデル（ソートでは swap と添字、todo では Vec の push など）
  • Lean のカーネル
ポイント「Rust と相性がよい」は「Rust なら全部証明できる」ではありません。別名の無い、safe な、小さい関数なら、手で Lean に書き直さずに済む、という意味です。

JavaScript はどこが難しいか

JavaScript には、Rust の借用検査に当たる仕組みがありません。証明しにくい理由を並べます。

性質証明で困ること
オブジェクトの共有と書き換えどの変数も同じオブジェクトを指せる。a.done = true で、別の名前から見た値も変わる。「新しい値を返す」に直すには、誰が何を指しているかを全部追う必要がある
動的な型引数に何が来るかは実行するまで分からない。TypeScript の型は実行時には消え、as で外せる
暗黙の型変換== や + が、値の種類によって違う規則で動く
例外どの呼び出しも投げうる。投げたかどうかが型に出ない
非同期とイベントループawait のたびに、ほかの処理が割り込める。結果は実行順で変わる
外界の APIlocalStorage・fetch・タイマー・DOM。どれも Lean の外にあり、動きを誰かがモデルにする必要がある

この book で調べた範囲では、Aeneas のように JavaScript のコードをそのまま Lean に翻訳して証明する、実用段階の道具は見つけられませんでした。

だから付録F は MBT、付録D はモデル検査にした

付録F の reduce は、書き換えをせず新しい状態を返すように、わざと純粋に書きました。スプレッド構文（...）でコピーを作り、元の state には触りません。

純粋なので、仕様から作った操作の列を流し、1歩ごとに Quint の状態と比べられます。ただし「純粋に書いた」ことは、人がそう書いただけです。Rust のようにコンパイラが保証してはいません。だから証明ではなく、実行列を流して突き合わせる MBT にしました。

付録D の sync.ts も中身は純粋な関数です。難しいのはそれを呼ぶ外側で、localStorage・fetch・setTimeout が絡みます。

付録D で見つけた不具合は、どれも「送信・失敗・遅れた応答・別のタブの操作がどの順に起きるか」で起きました。これはコードの1行ずつではなく、タイミングの組み合わせの問題です。そこでコードを翻訳するのをやめ、2つのタブとサーバの動きを手で TLA+ にモデル化しました。手で書いたモデルとコードがずれる危険は残ります。

ほかの道具

  • Rust 側：Verus（Rust のソースに事前・事後条件を書き SMT で検査）、Kani（テストのように書いたハーネスを有界に全部調べる）、hax（Rust を F*・Rocq や、Aeneas 経由で Lean などに翻訳）があります。
  • JavaScript を「書く」のではなく「出す」道：Dafny は、証明したコードを C#・Go・Python・Java・JavaScript に変換できます。JS のコードを証明するのではなく、証明した言語から JS を生成する道です。
  • 言語を揃えない道：認可ポリシーの言語 Cedar は、Lean で書いたモデルと証明を持ち、本番の Rust 実装とは乱択の差分テストで突き合わせています。仕様は Lean、実装は別の言語、という付録F と同じ形です。

付録D TLA+ と TLC で同期を検査する

オフラインでも動く todo アプリを2つのタブとサーバのモデルにして、送信・失敗・遅れた応答がどの順に起きても約束が守られるかを全部調べます。テストが全部緑のアプリから、操作が黙って消える不具合を3つ見つけます。

この付録のゴール

  • 楽観的更新・送信待ち・再送・opId・version・seq の役割を説明できる
  • 同期の不具合がテストで見つかりにくい理由を「タイミングの組み合わせ」で説明できる
  • TLA+ で「状態」と「遷移」を書き、性質を不変条件として書ける
  • TLC の反例を、画面の操作の手順として読める
  • 「範囲」と「モデルに入れていない操作」が見逃しを生むことを、実例で知る

題材：同期つきの小さな todo アプリ

題材は todo/ フォルダの、Bun・TypeScript・SQLite で書いた web アプリです。追加・名前の変更・完了の切り替え・削除ができ、複数のタブや端末から同じ一覧を使えます。

回線が切れていても画面は動き、変更はつながったら送られます。この「あとで送る」部分を検査します。

  1. 同期の仕組みを部品に分ける

    README の「同期の設計」にある部品は次の6つです。

    • 楽観的更新：サーバの返事を待たずに画面を変えること。画面には、サーバから最後に聞いた行（confirmed）に未確認の操作を当て直したものを出します。
    • 送信待ち（outbox）：サーバの確認がまだ来ていない操作の列。操作した順に並び、先頭から送ります。
    • 再送：失敗・タイムアウト（5秒）・応答の消失を区別せず、同じ操作をもう一度送ること。間隔は 0.5 秒から倍々、上限 10 秒です。
    • opId：操作ごとの名札で、形は クライアントID:連番。サーバは反映した opId を記録し、同じ opId は二度反映しません。
    • version：todo ごとの版の番号。変わるたびに 1 増え、手元より大きい行が届いたときだけ置き換えます。
    • seq：サーバ全体の通し番号。各行に最後に変わったときの seq が付きます。クライアントは取り込んだ位置（lastSeq）を覚え、2秒ごとにそれより新しい変更を取り込みます（pull）。

    クライアント ID はタブごとの保存場所 sessionStorage に置きます。送信待ちを含む状態全体は、ブラウザ全体で共有される localStorage に、クライアント ID ごとのキーで保存します。

    sequenceDiagram
  participant U as "ユーザー"
  participant T as "タブ"
  participant S as "サーバ"
  U->>T: "完了にする"
  T->>T: "opId c1:2 を送信待ちに積む・画面をすぐ変える"
  T->>S: "push（送信待ちの先頭から）"
  S-->>T: "応答が消える"
  T->>S: "同じ c1:2 を再送"
  S->>S: "c1:2 は反映済みなので二重にしない"
  S-->>T: "results に c1:2"
  T->>T: "送信待ちから c1:2 を外す"
  T->>S: "pull（lastSeq より新しい変更）"
  S-->>T: "変更された行と seq"
    ポイントこの設計の要は「opId が同じなら同じ操作」という約束です。サーバは opId だけで再送か新しい操作かを決めます。

  2. なぜテストでは見つかりにくいのか

    このアプリのテスト 18 件は全部緑です。再送、2台の同時編集、削除と編集の競合、オフラインからの復帰まで試しています。

    それでも、テストは書いた順番しか試しません。同期では次の出来事がどの順にも起きます。

    • タブ1で操作する・タブ2で操作する
    • 送る・送る前に失敗する・サーバに届く・応答が届く・タイムアウトで諦める
    • pull する・pull の応答が届く
    • リロードする・タブを複製する・タブを閉じる

    タブ2つでも、並べ方は人が書き切れない数になります。テストが鍵を数本試すことなら、これから使う道具はありうる鍵を全部試すことです。

  3. TLA+ で「状態」を書く

    TLA+ は、システムを「状態」と「遷移」で書く仕様の言語です。TLC は TLA+ のモデル検査器で、遷移を全部の順番でたどります。付録F の Quint は、TLA+ の考え方を読みやすい文法にしたもので、検査に同じ TLC を使えます。

    モデル todo/verification/SyncTodo.tla では、まず状態を変数で書きます。タブごとの値は「タブ → 値」の対応で持ちます。

    コメントに対応するコードの名前があります。モデルはコードを読まないので、この対応は人が付けています。

    コードに無い変数はゴースト変数で、性質を書くためだけの記録です。made はユーザーが積んだ操作の全部、acked は確認が来て送信待ちから外した操作です。

  4. TLA+ で「遷移」を書く

    遷移1つをアクションと呼びます。x' は次の状態での x、/\ は「かつ」、UNCHANGED は変わらない変数です。[pushing EXCEPT ![t] = n] は「タブ t の値だけを n に替えたもの」です。

    区切り方は「await を挟まない1区間を1アクションにする」です。JavaScript は1スレッドなので、その区間には何も割り込みません。await の前後は分け、間に何が起きてもよいようにします。

    送信の始まりでは、送信中でなく送信待ちが空でなければ、先頭から最大 50 件を送ります。

    失敗やタイムアウトは「諦める」アクションです。送信中の印を外すだけで送信待ちは残るので、次の送信で同じ opId のまま再送されます。

    タブの複製もアクションです。ブラウザの仕様で sessionStorage が写るので、複製したタブは同じクライアント ID になり、localStorage の同じキーから状態を読みます。

    最後に、ありうる遷移を「または（\/）」でつなぎます。\E t \in Tabs : … は「どれかのタブ t で」です。Spec の行は決まり文句です。

  5. 守ってほしい4つの性質を書く

    性質は不変条件で書き、TLC がたどった全状態で確かめます。

    • AckedMeansApplied：送信待ちから外した操作は、その操作としてサーバに反映されている。破れると、変更が黙って消えたまま「同期済み」と出ます。
    • ClientOrderKept：同じクライアント ID の操作は、サーバで連番の順に1回ずつ処理される。破れると、遅れた古い再送が新しい値を巻き戻します。
    • Converged：送信待ちも途中の要求も無く全タブが pull し終えたら、全タブの一覧がサーバと同じ。破れると、タブごとに違う一覧が直りません。
    • NoOpLost：積んだ操作は、サーバに反映済みか、開いているタブの送信待ちか、途中の要求にある。破れると、操作がどこからも送られなくなります。
    ポイント4つとも「どう守るか」ではなく「何が守られていればよいか」を書いています。仕様を実装の都合から切り離すためです。

  6. 範囲を決めて TLC で全部たどる

    全部たどるには世界を有限にします。設定ファイル（.cfg）で、todo の数や操作の回数に上限を付けます。2枚目のタブを「同じ URL を別タブで開く」か「複製する」かもここで選びます。

    この設定では4つとも成り立ちます（1,499,907 状態・1ワーカーで約 90 秒）。設定は6つあり、入れる操作が違います。

    • SyncTodo.cfg：別タブで同じ URL を開く・リロードあり・todo 1件。4つとも成り立つ
    • SyncTodoTwoTodos.cfg：同じで todo 2件・push 2回まで。4つとも成り立つ（651,021 状態・約 40 秒）
    • SyncTodoDuplicateTab.cfg：タブの複製。AckedMeansApplied と NoOpLost が破れる
    • SyncTodoDuplicateReload.cfg：複製＋リロード。NoOpLost と AckedMeansApplied が破れる
    • SyncTodoCloseTab.cfg：タブを閉じる。NoOpLost が破れる
    • SyncTodoStaleUI.cfg：編集中で描き直しが止まった古い画面からの操作も加えた版。4つとも成り立つ（16,004,587 状態。重いので任意）
    やってみようTLC は、pstack（AI エージェント向けのスキル集）の statechart スクリプトから呼びます。反例を「タブ1・タブ2・サーバ」の言葉の手順に直してくれます（view.mjs）。todo/ フォルダで、S にスクリプトのパスを入れて5つの設定を回します。初回は TLC と Java を入れるのでネットワークが要ります。 
    S=<pstack の skills/statechart/scripts/statechart のパス>
V=verification; O=$(mktemp -d)
for c in SyncTodo SyncTodoTwoTodos SyncTodoDuplicateTab SyncTodoDuplicateReload SyncTodoCloseTab; do
  echo "=== $c"; "$S" "$V/SyncTodo.tla" --config "$V/$c.cfg" --view "$V/view.mjs" --out "$O/$c"
done
    SyncTodo と SyncTodoTwoTodos の報告の「Rules that hold」に4つ並べば正常です。残り3つは破れるのが今の正常です。

  7. 反例を手順として読む（発見1 タブの複製）

    性質が破れると、TLC はそこに至る最短の手順（反例）を出します。反例はそのまま再現手順です。

    SyncTodoDuplicateTab.cfg では AckedMeansApplied が 9 ステップで破れます。画面の言葉にすると次のとおりです。

    1. タブ1で todo「A」を追加する（op c1:1）
    2. タブを複製する。sessionStorage が写るので同じ ID c1、同じ状態（次の連番は 2）になる
    3. タブ1で名前を「B」に変える → op c1:2
    4. タブ2で完了にする → これも op c1:2
    5. 両方が送る。サーバは先に届いたタブ1の c1:2 を反映し、あとのタブ2の c1:2 を「再送」と見なして反映しない
    6. タブ2は応答に c1:2 があるので送信待ちから外し、「同期済み」と出る。サーバの todo は「B」未完了のまま
    flowchart LR
  A["タブ1 c1:2 名前をBに"] --> S["サーバ c1:2 を反映"]
  B["タブ2 c1:2 完了にする"] --> R["サーバ 反映済みの c1:2 と見なす"]
  R --> X["タブ2 送信待ちから外す・同期済みと表示"]
  X --> L["完了の操作が消える"]

    「opId が同じなら同じ操作」という約束が、複製で崩れました。重なったのが追加なら、その todo は作られず画面からも消えます。

  8. 反例を読む（発見2 保存の上書き・発見3 タブを閉じる）

    発見2：複製したタブ同士が保存を上書きし合う。2つのタブは同じキー todo-state:c1 に保存するので、リロードすると最後に保存したもう一方のタブの状態を読みます。SyncTodoDuplicateReload.cfg で NoOpLost が 5 ステップで破れます。

    1. タブ1で追加する
    2. タブを複製する
    3. タブ1で名前を変える（c1:2 名前）
    4. タブ2で完了にする（c1:2 完了。保存が上書きされる）
    5. タブ1をリロードする → タブ1の送信待ちが「1:追加・2:完了」になり、名前の変更が消える

    発見3：送信待ちが残ったタブを閉じると、二度と送られない。ID はそのタブの sessionStorage にしか無く、開き直すと新しい ID になり、古いキーは誰も読みません。SyncTodoCloseTab.cfg で NoOpLost が 2 ステップで破れます。

    1. タブ1で追加する
    2. タブ1を閉じる

    反例はモデルの上の話なので、モデルの書き間違いもありえます。3つとも本物のコードで手順を流して再現し、本物の不具合と確かめました。

    ポイントREADME の「同じ URL を別タブで開くと別のクライアントになる」は複製で、「変更は送信待ちに残り、つながったら送られる」はタブを閉じると成り立ちません。検査は、設計書の言葉が破れる場面を手順で示しました。
    落とし穴「クライアント ID を起動ごとに作り直す」直し方は誤りです。リロードのたびに新しいキーを読み、発見3と同じ消失が毎回起きます。直したらモデルも同じ意味に直して回し直します。

  9. 見逃しの形を知る

    最初の検証では SyncTodo.cfg が全部緑でも、不具合は残っていました。理由は2つです。

    1つ目：範囲が小さすぎると出ない不具合がある。todo 1件では push の応答の行がいつも最新版なので、「push の応答で lastSeq を進める」誤りは原理的に出ません。わざと入れて試すと、todo 1件では素通りし、SyncTodoTwoTodos.cfg で 11 ステップの反例が出ました。2件の設定はこのために足したものです。

    2つ目：モデルに無い操作は調べようがない。最初のモデルにはリロードとタブを閉じる操作が無く、監査で指摘されて足したら発見2と3が出ました。TLC は書かなかった遷移を一度もたどりません。

    落とし穴今のモデルにも無いもの：3枚目のタブや複製の複製、50 件を超える分割、pull のページ送り、localStorage への保存の失敗、「いつかは同期が済む」こと（活性）。コードを変えてもモデルは変わらないので、モデルを直さずに回した緑は何も示しません。
    やってみよう検査が働くかは、わざと壊して確かめます。SyncTodo.tla の SameOpId（いまは a.cid = b.cid /\ a.no = b.no）を a.no = b.no だけにして SyncTodo.cfg で回すと、別タブの連番 2 を取り違える 10 ステップの反例が出るはずです。確かめたら元に戻します。

まとめ

  • 同期は楽観的更新・送信待ち・再送・opId・version・seq の組み合わせで、要は「opId が同じなら同じ操作」
  • テストは書いた順番しか試さない。TLC は書いた遷移を全部の順番でたどる
  • 1アクションは「await を挟まない1区間」。性質は「何が守られていればよいか」を不変条件で書く
  • テスト 18 件が緑のアプリから、タブの複製・保存の上書き・タブを閉じる、で操作が消える不具合を3つ見つけ、本物のコードで再現した
  • 見逃しは「範囲が小さい」と「モデルに無い操作」から出る。検査はモデルに書いたことしか守らない

付録E h5i と Nyxis：web アプリの枠組みごと認可を証明する

第2章の認可の証明は Rust の中核までで、保存や本人確認は証明の外でした。この付録では、DB と HTTP まで含めた web アプリの枠組みで同じ認可を証明する2つの道具、h5i と Nyxis を見ます。

この付録のゴール

  • h5i で「判断をカーネルに集めて証明する」形が分かる
  • Nyxis で人が承認するものが分かる
  • 3つの道具（todo-aeneas・h5i・Nyxis）で、証明の範囲と外に残るものを比べられる

  1. h5i で DB と HTTP まで付ける

    h5i は Rust の web フレームワークです。判断をカーネル（DB・時計・通信に触らない純粋な関数）に集め、第1章と同じく Aeneas で証明します。サーバは受け渡しだけです。

    返す書き込み1つ1つが許されるかは、仕様の allowed で定めます。

    主な定理です（h5i app check で 108 定理、sorry なし。公理は Lean 標準の3つだけ）。

    • authorized_reachable: 成功したコマンドの書き込みは本人の todo だけ
    • others_unchanged: 他人の todo は1件も変わらない
    • list_own: 一覧は本人の todo ちょうど
    • Effects.*_effect・Effects.*_ok: 手順2の「中身」と「成功する」
    • Storage.db_inv: DB に書いて読み戻しても不変条件が保たれる
    やってみよう

    証明と変異テストを流してサーバを起動し、「他人の todo を id 指定で触ってみる」欄で bob からアリスの todo を消してみます（Docker が要ります）。

    cd h5i-todo

  2. 安全性の外を定理で埋める

    第2章で見たとおり、安全性の定理だけなら何でも断るカーネルでも通ります。todo-aeneas は「実装＝仕様」で埋めましたが、h5i 版にはそれに当たる定理が最初はありませんでした。

    落とし穴「改名で新しいタイトルを無視する」「完了フラグを勝手に戻す」カーネルも通ります。h5i 版の最初の版はこの状態で、レビューで指摘されました。

    そこで2種類の定理を足します。Principal は操作した人、Snapshot は状態です。

    • やったことの中身（*_effect）: 成功したコマンドが何を残し、何を返すか
    • 成功する（*_ok）: 持ち主の正しい操作は必ず成功する

    変異テストは設定ファイルに「置き換える文字列」を書いて行います。

    安全性の定理は通ってしまい、「中身」の定理で初めて捕まります。

    落とし穴変異テストは 15/15 で検出しましたが、これは「どこかで止まった」数です。15 件とも止まったのは途中の補題（Commands.lean）で、主張が偽になったとは限りません。

  3. Nyxis で「ポリシーとスキーマだけを人が承認する」

    Nyxis は Lean 製のバックエンドフレームワークです（サーバーが Lean で動く仕組みは付録B）。人が承認するのは Cedar（認可のルールを書く言語）の2ファイルだけです。

    • スキーマ: データとアクションの定義。テーブル定義も兼ねる
    • ポリシー: 誰がどのアクションをしてよいか。書いていない操作はすべて拒否

    リクエストを処理するハンドラは AI に書かせてよい部分です。型の上で認可層にしか頼めず、DB に直接届きません。主体（操作している人）は JWT（ログインが発行する署名つきの札）から決まります。

    本文で持ち主を偽っても効きません。

    lake build のたびに、「出された操作はすべて主体と一致し、ポリシーの範囲内」という定理が検査されます。

    本物のログインと DB を通す run.py check は 38 件通過しました。他人・匿名・偽や壊れた JWT での操作はすべて 403 で、DB は変わりません。

    認可層を迂回する試み2通りも、Lean のカーネル（証明を検査する部分。h5i のカーネルとは別物）とビルド時の監査（nyxis_check_app）が拒否しました。試したのはこの2通りだけです。

    落とし穴ポリシーを when { true }（誰でも何でもできる）にしても定理は通り、止めたのは #guard（具体例のテスト）10 本だけでした。ポリシーの中身は人とテストが見ます。

  4. それでも本人確認は証明の外

    DB と HTTP まで付けても、「本当にアリスか」はどちらも証明していません。

付録F Quint で仕様を全部の状態について調べる

本編では Lean で「どんな件数でも仕様どおり」と証明しました。この付録は別のやり方です。証明はせず、範囲を小さく区切って、起こりうる状態を機械に全部調べさせます。最後に、仕様から作った操作の列を JavaScript アプリに流して突き合わせます。

この付録のゴール

  • todo アプリを「状態」と「操作」で書ける
  • 不変条件を書き、quint test / quint run / TLC で調べられる
  • わざと壊した仕様で、検査の強さを測れる（変異テスト）
  • 仕様から作った操作の列でアプリをテストする（MBT）流れが分かる
  • 検査が緑でも残る見逃しを4つ言える

題材と道具

題材は todo アプリで、操作は追加・完了の切り替え・削除・題名の編集・全部切り替え・完了済みを消すの6つです。

道具は Quint（クイント）です。システムの決まりを書く言語で、見た目は TypeScript に似ており、書いた仕様を実行も全状態の検査もできます。版は 0.34.0 です。

証明との違いは、手間と保証の広さです。証明は手で組み立てる代わりに全部の件数で言えます。Quint は書くだけで機械が調べてくれますが、言えるのは調べた範囲の中だけです。

Quint で書くのはアプリではなく、アプリの決まりです。アプリは JavaScript で書き、後半の MBT でつなぎます。

  1. 状態を書く

    状態（アプリが覚えていること）は、todo の一覧と次に振る id の2つです。Quint では var で宣言します。

    last… と prev… は検査用の記録で、手順7で使います。アプリの状態は todos と nextId だけです。

  2. 操作を書く

    状態を変える操作を action（アクション）と呼びます。todos' のように '（プライム）を付けた名前が操作後の値です。

    all { … } は「中の条件が全部成り立つ」です。

    空白を INPUTS の表で取るのは、Quint に trim が無いからです。

    最後に、1歩ごとに6つのどれかが起きると書きます。

    nondet は「この中のどれでもよい」、any { … } は「どれか1つが起きる」です。

    ポイント仕様は「この順に呼ぶ」手続きではなく、「どの状態からでも6つのどれかが起こりうる」という可能性の全体です。

  3. 不変条件を書く

    第1章と同じく、どの操作の後でも成り立ってほしい性質（不変条件）を書きます。

    1つの状態を見れば言えるので、形の性質と呼びます。

  4. 具体例で動かす（quint test）

    まず具体的な操作の列で動きを確かめます。単体テストと同じ感覚です。

    .then(…) は「続けてこの操作」、.expect(…) は「最後にこれが成り立つ」です。具体例は4本です。

    動かすときは、上限などの定数を埋めた版を選びます。

    やってみよう具体例4本を流します。

    quint run は最大30歩の列をランダムに1万本試し、不変条件が破れたらそこまでの列（反例）を見せます。

    ランダムでは通らない道が残るので、到達できる状態を1つ残らず調べる TLC も使います（この手法をモデル検査と呼びます）。

結論

  • 「証明を書く手間」は2026年にほぼ機械の仕事になった。 数学ではフェルマーの最終定理（FLT）の形式化が11日で済んだ。ソフトウェアでは libsignal の機械語に対する650万行の証明を、人が1行も書かずに4週間で仕上げた。今後数年の争点は、証明できるかではなく、何を証明したことになるかに移る。
  • 律速は仕様と信頼の基盤（何を信じた上での証明か）に移った。 参照仕様の約半分が誤っていた例、検査器を書き換えて満点を取る AI、カーネルの健全性バグが出ている。これはハッカソンで得た「律速は人の理解」と同じ形で、数学・暗号・政策の現場でも同じことが観測されている。
  • 〜2029年に普及の中心になるのは重要インフラ（暗号・クラウドの分離・zkVM・Rust の核）。 「AI が全部を証明し、人は仕様だけを承認する」型が標準になる見込みが高い。
  • 一般の Web/SaaS に届くのは定理証明ではない。 要件からプロパティテスト（PBT）を作る、設計をモデル検査にかける、AI の出力を規則と照合する、といった軽量手法がエージェントに組み込まれる形が先に来る。業務ロジック全体の証明は2031年でも少数派。
  • Anycloud にとっての「今やる」は、仕様を読み書きする力と軽量手法の常用化。 証明まで入れるかの判断は2027年末に見直せばよい。

1. いま何が起きているか（2025〜2026年の変化点）

数学: 競技レベルは飽和し、大型の形式化は週の単位になった - 形式証明の IMO の成績は、2024年の銀（28/42）から2026年の満点（42/42。Axiom、全6問を Lean で約7,700行）まで伸びた（AxiomMath/IMO2026）。 - PutnamBench は2025年7月に50%前後、2026-08-25 に 672/672（約$5万）（Aleph）。翌月には約$111 で全問を解いたという報道もある（報道・未確認）。 - FLT の形式化は約1,300万行（Mathlib の5倍超）を11日でほぼ自律的に作った（Anthropic, 2026-09-04）。球充填の24次元は2週間（Math Inc.）。 - ただし研究水準の未解決問題（FrontierMath Erdős の68問）で解けたのは、まだ 2/68＝3% だけ（Epoch, 2026-09-01）。

重要インフラ: 「人は仕様だけ承認」が実例として出た - DeepMind の AlphaProof Code は、libsignal の AArch64 機械語に対する約650万行の証明を40〜80体のエージェントで書いた。人間5人は仕様約2.6万行を承認しただけ（TNW, 2026-11、confidence medium）。 - AWS の Nitro Isolation Engine はハイパーバイザの分離を Isabelle の約26万行で証明し、第三者による検査にも提供する（AWS ブログ）。 - Apple は耐量子暗号（ML-KEM/ML-DSA）を検証の成果物と一緒に公開し、テストでは見つからなかった欠陥も見つけた（Apple）。 - Anthropic と Theorem は OSS-Fuzz の123ライブラリについて、バイナリが落ちないことを約1.8億行の Rocq 証明で示した（Anthropic, 2026-10-22）。

AI が書くコード: 関数単位は解け、リポジトリ単位は半分 - 仕様が与えられた関数単位の検証付きコード生成は、Lean でもエージェントループで約95%に達した（arXiv 2605.27485）。Rust→Lean は1定理あたり約$1.2（中央値）（VeriContest）。 - 実プロジェクト43件を Lean で作り直す課題では、全仕様を通したのが最良でも27件（Vero）。 - Python→Lean で正解の仕様をどれだけ覆えたかは、どのエージェントでも0.156以下（VeriBench）。

ツールと資金 - Lean FRO は「主な使い手は AI エージェント」へ舵を切った。計画を半年単位に変え、外部カーネルでの再検査（lake check）や lean-beam を重点に置いている（Y4-1）。Lean 4.36 には関数の契約（contract）と vcgen が実験的に入り、MCP も同梱された（v4.36.0）。 - 資金調達は Axiom の Series A が$2億（SiliconANGLE）、&Truth のシードが$7,000万で「仕様の工場」をうたう（Pulse 2.0）。ただし顧客も売上もほぼ開示されていない。

2. 駆動力と制約

駆動力 1. AI 証明器の急伸と値下がり。 飽和したベンチマークでは、数週間で費用が2桁下がる（上記の PutnamBench）。オープン重みのモデルも約1年遅れで追ってきている（36Kr・未確認）。 2. AI が生成するコードの検証需要。 人のレビューが追いつかないという新しい「破局の物語」がある。Kleppmann は「AI が形式検証を主流にする」と予測した（2025-12）。 3. 移行の窓。 耐量子暗号への移行、zkVM を L1 に入れるまでの期限（EF）、Rust への移行（Rust std の検証、hax 0.4）。 4. 政府資金。 DARPA IPTO は部局全体の BAA で「レジリエンスには形式手法を推す」と明記した（BAA 2026）。ARIA は検証ツールの基盤とサイバー防御に £22m を回した（ARIA）。

制約 1. 仕様の正しさ。 Clever の参照仕様は161件中80件が誤っていた（2605.23772）。AI に仕様を書かせると、何も主張しない空虚な定理に逃げる（VeriBench）。LLM は並行性や liveness を書けない（Wayne）。ARIA の責任者も「証明は仕様と前提以上には強くならない」と認めている（Ammann）。 2. 検査器への攻撃と健全性。 エージェントが公理の監査コマンドを差し替え、カーネル検査を飛ばして満点を取った例がある（Vals AI）。native_decide のバグで偽の FLT 証明が通り（Trail of Bits）、Lean カーネルの False 証明バグも2件出た（oss-security）。 3. 「検証済み」の水増し。 仕様の誤りや admit を指摘した Verification Theatre、検証器を報酬にした強化学習の仕様ハッキング（2605.30914）。 4. 保守とコスト。 証明はコードの変更で壊れる。障壁の上位は専門性・ツールの性能・保守（ETH 調査）。AI 製の証明は膨れ上がり、自然言語18ページが Lean で120万行になった（Epoch）。速く変わる Web のコードは対象外という実務家の見方も続いている（AkitaOnRails）。 5. 規制は形式検証を求めていない。 CISA/NSA が求めるのはメモリ安全言語まで（CISA）。EU CRA も脆弱性対応と説明責任が中心（EC）。ARIA 自身も、検証を通った AI だけを配備させる規制で国際合意ができる見込みは下がったと書いている（thesis v2）。

4. シナリオ3本と先行指標

  • 強気（20%）: 仕様の生成とレビューも AI で安くなり、2029年にはエージェントが Web の業務ロジックにも契約と証明を付けるのが既定になる。
  • 中央（55%）: 重要な核（暗号・カーネル・プロトコル・zkVM・Rust の unsafe）は「AI が証明し、人は仕様を承認」が標準になる。一般開発は PBT・モデル検査・実行時の監視がエージェントに組み込まれる形で広がり、証明は核に限られる。
  • 弱気（25%）: 「検証済み」を名乗った製品の事故（仕様の誤り・検査器のすり抜け）が続いて信頼を失い、Hoare（1996）型の「テストと運用で十分」という反論が戻る（Hoare）。投資は2028年ごろに縮む。

見分ける先行指標 - 2027年末までに Vero 型のリポジトリ単位で全完了が80%を超える → 強気寄り。50%前後で止まる → 中央。 - 2027年前半までに Claude Code・Codex・Cursor のどれかが Lean・Dafny・Verus の検証を既定で同梱する → 強気。 - 2027年に FrontierMath Erdős を再測定して20%を超える → 数学は強気。10%未満 → 減速。 - Thoughtworks Radar で TLA+・Quint が Assess から Trial に上がる（TLA+、Quint） → 軽量手法の主流化。 - Axiom・&Truth・Harmonic が有償の顧客名と導入事例を2028年までに公表する → 事業として成立。公表が無いまま次の調達が難航する → 弱気。 - 「検証済み」の誤りが大きく報道される件数と、lake check や独立カーネルでの再検査が標準手順になるかどうか。

5. 普及の形の予想（見立て）

  1. 仕様は人が読み、証明は機械が書く。 レビューの対象がコードから仕様に移る。仕様言語は「人が読みやすいか」で選ばれる（Quint が評価された理由）。
  2. 受理の手順が工程として独立する。 クリーン環境での再ビルド、公理の許可リスト、独立カーネルでの再検査、仕様のミューテーション（わざと壊して検出できるか確かめる）。証明を書くことより、受け入れる手順のほうが製品になる。
  3. 軽量手法がエージェントに溶ける。 要件→性質→PBT（Kiro）、設計→モデル検査、本番ログと仕様の照合（AWS の PObserve。CACM）、LLM の出力を規則と照合（Bedrock）。
  4. 検証済みの核を呼び出す。 Rust や Lean で証明した部品を TS や Python から呼ぶ（Lean の Python FFI「Nerodia」など）。アプリ全体を検証言語で書くのではない。
  5. 1つの重要な性質に絞る。 「全部」ではなく、利用者に害が出てテストでは届きにくい性質を1つ選んで検証する型が実務に定着する。テストや人のレビューを置き換えず、その上に重ねる層になる（SPARK の事例）。

6. Anycloud と村井さんにとっての意味

今やる（2026年12月〜） - 仕様を書いて読む力を、チームの中核スキルとして扱う。 証明が安くなるほど、価値は「何を保証させるか」を決める人に寄る。受託では、顧客の要件を検査できる性質に言い直す作業がそのまま差別化になる（見立て）。 - TS の業務ロジックの核（認可・課金・状態遷移・データ移行の突合）に fast-check で PBT を入れ、要件→性質の変換はエージェントに書かせる。 費用が最も小さく、効果がすぐ出る。 - 並行・分散の設計（ジョブの排他ロック、ループの取り込み、二相コミットのような流れ）は、新しく作るときだけ Quint か TLA+ で状態機械を書いて反例を探す。 ハッカソンの「新しく入れて割に合う所は少ない」と矛盾しない。対象を新規の設計に限ればよい。 - AI の成果物を「受け入れる手順」を整える。 既存の検証の実践（skip を green と読まない、検証器をわざと壊して検出を確かめる）を、AI が書いたテストや仕様にもそのまま当てる。これは形式検証の受理の手順と同じ考え方。

2027年末に見直す - Lean の契約（contract）が安定したか、TS の検証層（LemmaScript の類）が実務水準に育ったか。 - 主要エージェントが検証を同梱したか、Vero・VeriBench の値がどこまで伸びたか。 - Rust の核（暗号や解析器など）を持つ案件が出たら、Aeneas や Verus で1定理あたり約$1 の証明を試す価値が出る。

待つ - Web/SaaS のアプリ全体の証明、Lean を本番の Web サーバに使うこと。Lean の HTTP は HTTP/1.1 だけで若く、コンパイラの性能改善の実装も2027年からなので、早くて2028年以降。 - 証明を前提にした受託の商品化は、顧客の側に支払う理由（規制・調達）が無いので2029年まで待つ。例外は、金融・決済・ブロックチェーンのように「バグがそのまま資金の損失になる」顧客。

村井さん個人: 発信する立ち位置は「証明の自動化」より「仕様と受理の設計」に置くと、数年で古びにくい（見立て）。Lean は読める状態を保ち、追うのは FRO の半年ごとのロードマップで十分。

7. 不確実性と、外れるとしたらどこか

  • 仕様の自動化が予想より速く進む場合（強気側に外れる）。 「AI がベンチマークの形式化の誤りを28件見つけた」（Aleph）や&Truth の「仕様の工場」が効けば、人の理解という律速そのものが緩む。この初稿で最も外れやすい前提。
  • 数学の伸びがコードに移る遅れ。 1〜2年と置いたが、リポジトリ単位の整合（補題の深さ、ビルド、性能要件）が難しく、もっと遅れる可能性もある。
  • 信頼の事故。 「検証済み」の大きな事故が1件起きれば、弱気シナリオに一気に寄りうる。
  • 資金の持続性。 顧客の開示が無いまま評価額が先行している。Lean 系は慈善資金に依存している（AI for Math Fund）。
  • 出典の確度。 AlphaProof Code（論文本文は未確認）、NEAR の$111、オープン重みの数字、Certora の件は二次情報で、confidence は low〜medium。モデル名は出典の記載どおりで、公開状況は確かめていない。
  • 「普及」の定義。 PBT やモデル検査まで含めるか（AWS 流の広い定義）、証明だけに限るかで結論が逆になる。この初稿は、広い定義では普及し、狭い定義では核に限られる、という両方を書いている。
